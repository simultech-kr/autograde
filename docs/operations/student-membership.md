# 학생 회원가입과 수강 명단 자동 연결

학생은 학번·본인 비밀번호로 먼저 가입하고 운영 중인 수업 목록에서 수강할 수업을 선택한다.
신규 계정은 교수자가 별도로 본인을 확인해 발급한 일회용 활성화 코드를 입력해야 한다.
본인 확인과 해당 수업의 학번 명단 일치가 모두 완료되면 수강 연결된다. 학교 SSO는 사용하지 않는다.
계정·수강 명단·연결 상태는 SQLite에 저장하며, 이 기능 때문에 새 환경변수나 별도 DB 서버를 준비하지 않는다.

## 시작 주소

운영 서버에 갱신된 소스를 적용한 뒤 사용할 주소다. 문서 작성만으로 운영 서버에 적용되지는 않는다.

| 업무 | 주소 예시 |
| --- | --- |
| 학생 시작 | `https://ai.cbchoi.info:20010/student` |
| Next.js 학생 포털 | `https://ai.cbchoi.info:20010/app/student` |
| 새 학생 가입 | `https://ai.cbchoi.info:20010/student/register` |
| 공통 회원 로그인 | `https://ai.cbchoi.info:20010/student/login` |
| 내 수업·추가 수업 선택 | `https://ai.cbchoi.info:20010/student/account` |
| 회원 비밀번호 복구 | `https://ai.cbchoi.info:20010/student/reset` |
| COME2201 명단 관리 | `https://ai.cbchoi.info:20010/courses/come2201/instructor/registrations` |
| COME2201 명단 양식 | `https://ai.cbchoi.info:20010/courses/come2201/instructor/registrations/template.csv` |

IDE API 주소는 기존 `https://ai.cbchoi.info:20000`을 유지한다. 학생은 웹 회원 비밀번호 대신
수령 코드를 IDE에 입력한다. 웹 주소의 `20010`을 IDE API 설정에 넣지 않는다.

## 교수자: 수강 명단 등록

1. 교수자 포털에서 담당 수업을 연다. 새 수업이라면 수업 설정에서 운영 상태로 전환한다.
2. **가입·수강 명단**에서 **CSV 기본 양식 다운로드**를 누른다.
3. 예시 학번을 지우고 실제 해당 수업 학번을 입력하여 UTF-8 CSV로 저장한다. UTF-8 BOM도 허용한다.
4. 파일과 **명단 추가/허용 명단 교체**를 선택하고 **명단 변경 미리보기**를 누른다.
5. 신규·기존·중복·제외 인원과 본인 확인된 대기 신청 수를 검토한다. 아직 이 단계에서는 변경되지 않는다.
6. 확인란을 선택하고 **검토한 명단 반영**을 누른 뒤 추가·제외·수강 연결 결과를 확인한다.
7. 신규 학생의 본인을 별도로 확인한 뒤 **본인 확인·계정 복구 코드**에서 학번·사유·확인란을 입력하여 활성화 코드를 발급한다. 해당 학생에게 직접 전달한다.

가장 간단한 형식은 한 열이다. 학번의 앞자리 0이 사라지지 않도록 스프레드시트에서는 문자열로 입력한다.

```csv
student_key
20260001
20260002
```

한글 머리글도 허용한다.

```csv
학번
20260001
20260002
```

선택 사항으로 `student_key,name` 또는 `학번,이름`의 두 열을 사용할 수 있다. 이름은 연결 판정에
사용하거나 저장하지 않는다. 이 네 종류의 머리글만 허용하며 **비밀번호 열은 넣지 않는다**.
학번은 숫자 4~20자리, 파일은 최대 1 MiB·10,000명이며 중복 학번은 한 번만 반영한다.

기본 방식은 기존 명단에 **추가**한다. **교체**는 파일에 없는 학번을 허용 명단에서 제외하지만
이미 활성 수강 중인 학생을 중지하지 않는다. 실제 접근 중지는 기존 **학생 관리 → 수강 비활성화**에서
별도로 처리한다. 검토 화면은 15분 뒤 만료되며 다른 작업으로 명단이 바뀌면 재검토해야 한다.
명단과 본인 확인이 완료된 학생만 자동 연결된다. 업로드·반영·코드 발급 이력은 SQLite에 기록한다.

## 학생: 가입부터 과제 수령까지

1. 학생 시작 화면에서 **회원가입**을 연다.
2. 학번과 본인이 정한 8~128자 비밀번호로 가입한다. 가입 폼에는 수업을 입력하지 않는다.
3. 운영 중인 수업 목록에서 교과목·학기·분반을 확인하고 수강할 수업을 선택한다.
4. 교수자가 본인 확인 후 제공한 활성화 코드를 입력한다. 코드의 유효기간은 15분이며 한 번만 사용할 수 있다.
5. **내 수업**에서 본인 확인·명단 연결 상태를 확인한다. 명단과 일치한 활성 수업을 열 수 있다.
6. 연결된 수업에서 실습을 선택하고 과제 수령 코드를 발급한다.
7. IDE에 수령 코드를 입력하고 과제를 다운로드한다. 실습 후 공식 제출을 수행하고 결과를 확인한다.
8. 잘못 선택한 수업의 신청이 확인 대기라면 **수강 신청 취소**를 사용한다. 이미 수강 중인 수업은 교수자에게 중지를 요청한다.

명단 확인 대기라면 아직 수업 권한을 얻은 상태가 아니다. 학번·수업 선택을 확인하고 교수자에게
해당 명단 등록 여부를 문의한다. 학번을 바꿔 여러 계정을 만들거나 같은 비밀번호를 교수자에게 보내지 않는다.
명단을 나중에 올려도 자동 연결되므로 학생이 다시 가입할 필요는 없다.

학번 일치는 수강 자격 확인이다. 본인 확인 코드는 실제 학번 소유자를 확인한 후에만 전달한다.
새 코드를 발급하면 이전 미사용 코드는 무효가 된다. 코드 원문은 발급 응답에서만 표시하며 DB에는 해시를 저장한다.
코드를 받았다고 수업이 자동 선택되지는 않는다. 학생이 신청한 수업 중 명단이 일치하는 수업만 연결한다.
기존 파일럿에서 이미 만들어진 회원 계정은 갱신 시 기존 이용 권한을 유지한다. 새 계정부터 활성화 절차를 적용한다.

## 회원 비밀번호 변경·복구

- 로그인한 학생은 **회원 비밀번호 변경**에서 현재 비밀번호를 확인하고 새 비밀번호를 설정한다.
- 분실한 학생은 관리자에게 본인 확인을 요청한다. 관리자는 해당 수업의 명단을 확인하고 사유·본인 확인란을 입력하여 **회원 비밀번호 복구 코드**를 발급한다.
- 담당 교수자 권한만 가진 계정은 신규 활성화 코드를 발급할 수 있지만 공통 회원 복구 코드는 발급할 수 없다. 여러 수업이 사용하는 공통 계정에 영향을 주기 때문이다.
- 학생은 로그인 화면의 **회원 비밀번호 찾기**에서 학번·복구 코드·새 비밀번호를 입력한다. 복구 코드는 15분·1회로 제한되며 재사용·다른 학번·만료 코드는 거절한다.
- 다른 사람이 학번으로 먼저 가입한 경우에도 관리자가 실제 소유자를 확인하고 복구 코드를 발급할 수 있다. 미확인 계정의 비밀번호 복구는 계정 활성화를 대신하지 않는다. 새 활성화 코드를 별도로 발급하며 기존 미사용 코드는 무효가 된다.
- 변경·복구 후 공통 웹 세션과 현재 서버의 학생 웹 세션을 폐기하고 재로그인을 요구한다. 기존 6자리 수업 비밀번호와 IDE 인증은 별도 자격 증명이며 이 기능에서 교체하지 않는다.

## 기존 6자리 수업 비밀번호를 사용하는 학생

기존 수업 로그인은 유지한다. 이미 비밀번호가 등록된 학번을 새 회원가입에서 입력하여 기존 계정을
덮어쓸 수는 없다. 공통 회원 계정으로 연결하려면 다음 순서를 따른다.

1. 기존 `/courses/{교과목 코드}` 화면에서 학번과 기존 6자리 수업 비밀번호로 로그인한다.
2. **회원 계정 만들기**를 선택한다. 해당 경로는 `/courses/{교과목 코드}/activate-account`다.
3. 새 공통 회원 비밀번호 8~128자를 설정한다.
4. 이후 공통 로그인으로 본인 수업에 접근한다. 기존 6자리 수업 비밀번호는 바꾸거나 삭제하지 않는다.

공통 회원 비밀번호는 직접 수업 로그인에도 사용할 수 있다. 공통 계정 생성·연결은 기존 학생의
과제·제출·성적을 새 학생으로 복제하지 않는다.

## 로그인과 공용 PC 종료

공통 회원 로그인은 최대 **10분** 유지한다. 수업 페이지를 열 때 현재 계정·수강·수업 상태를 다시
검사한다. 수령 코드를 발급하면 수업별 임시 세션은 소비하지만 공통 회원 로그인까지 종료하지는 않는다.
공통 로그인 없이 기존 수업 비밀번호만 사용한 경우에는 코드 발급 후 수업에 다시 로그인한다.

학생은 공용 PC를 떠나기 전에 학생 웹에서 **로그아웃**하고 브라우저를 종료한다. IDE의 공용 실습
종료는 로컬 코드·자료·IDE 인증을 정리하는 별도 절차이며 브라우저 회원 쿠키를 지우는 기능이 아니다.
비밀번호나 수령 코드를 브라우저 자동 저장·공유 문서에 남기지 않는다.

### 인증 쿠키와 계정 전환

HTTPS 웹 주소로 설정한 경우 학생 인증 쿠키는 `Secure; HttpOnly; SameSite=Lax; Max-Age=600`을
사용하며 `Domain`을 지정하지 않는다. HTTP 파일럿 설정에는 `Secure`가 붙지 않으므로 외부 운영에는
HTTPS 웹 주소를 사용한다. 쿠키에는 비밀번호 대신 임의의 세션 식별자를 넣고, 서버에서도 만료·비밀번호
변경·수강 비활성화를 검사한다.

공통 회원 쿠키와 수업별 인증 쿠키는 `Path=/`다. 계정 전환 시 수업별 인증도 서버에 전달되어 이전 학생의
인증을 폐기한다. 로그인 화면의 CSRF 준비 쿠키는 별도 이름과 `Path=/student`를 사용해 현재 로그인 쿠키를
덮어쓰지 않는다. 여러 쿠키를 변경할 때는 각각의 `Set-Cookie` 응답 헤더로 전송한다.

공통 로그인 상태에서는 과제·자료·시험지의 로그아웃도 공통 로그인을 해제한다. 만료된 공통 로그인에서
과거 학생의 수업 쿠키로 되돌아가지 않는다. 기존 6자리 수업 로그인으로 전환하려면 해당 로그인 화면에서
명시적으로 인증해야 한다.

`Max-Age`가 있는 쿠키는 브라우저 종료만으로 즉시 지워진다고 가정할 수 없다. 공용 PC에서는 반드시
웹의 **로그아웃**을 사용한다. IDE 종료 후 파일 정리는 웹 로그인 해제와 별개다.

같은 호스트의 `20010`과 `20000`은 쿠키가 포트별로 격리되지 않는다. 두 서버는 동일한 신뢰 경계에 두고,
브라우저 웹 요청은 같은 출처의 경로를 사용한다. 제공한 Nginx 설정 예제는 Next.js 셸에 인증 헤더를 전달하지 않는다.
쿠키 동작 기준은 [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)와
[RFC 6265의 포트 격리 제한](https://www.rfc-editor.org/rfc/rfc6265#section-8.5)을 따른다.

### Next.js 시안과 운영 화면의 구분

`/app/preview/portal`은 예시 데이터로 화면을 체험하는 시안이며 실제 계정·수강 신청을 변경하지 않는다.
실제 Next.js 학생 포털은 `/app/student`이며 Python의 `/student/api/*`를 같은 출처로 호출한다.
Next.js 배포와 Nginx 연결을 하지 않은 환경에서도 기존 Python `/student/*` 회원 화면을 사용할 수 있다.
두 화면 모두 계정 생성과 수강 선택이 분리되어 있고 동일한 SQLite 계정·명단·세션 검사를 사용한다.

## 관리 범위와 현재 제한

- 담당 교수자는 자신의 수업 명단만 관리한다. 다른 수업의 명단과 회원 비밀번호는 조회하지 않는다.
- 기존 **학생 관리**에서 수강을 비활성화하면 해당 수업 접근이 차단된다. 명단 재업로드로 비활성 수강을 자동 복구하지 않는다.
- 허용 명단 교체는 수강 중지와 별개다. 교체 후 제외된 학생도 이미 활성 수강 중이라면 접근을 유지한다.
- 교과목 영구 삭제는 해당 수업의 명단·수강 연결을 제거한다. 다른 수업에서 사용하는 공통 회원 계정은 유지한다.
  파일과 데이터 보존 범위는 [교과목 영구 삭제](course-permanent-deletion.md)를 따른다.

교수자·학생 화면의 전체 이동 경로는 [포털 운영 안내](role-portals.md)를 참고한다.

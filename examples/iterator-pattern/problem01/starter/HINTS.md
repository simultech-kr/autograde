# Iterator 실습 구현 힌트

README의 동작 규칙과 평가 ID를 기준으로 점검합니다. 아래 힌트는 수정 방향이며, 실패 원인을 단정하는 진단이 아닙니다. 여러 항목이 동시에 실패하면 먼저 Iterator 생성 경로와 공통 TODO의 미완성을 확인합니다.

## 구현에 필요한 상태

`ScoreIterator` 하나가 스냅샷 `snapshot_`, 기준 점수 `minScore_`, 다음 후보 위치 `position_`를 소유합니다. `position_`는 0 이상 스냅샷 크기 이하입니다. 크기와 같으면 끝이며, 범위 안이면 다음에 반환할 일치 기록을 가리킵니다. 이 조건을 생성·반환·초기화 뒤마다 유지하면 `hasNext`가 단순해집니다.

`advanceToMatch`의 반복 조건은 두 부분입니다. 먼저 위치가 범위 안인지 확인하고, 그다음 해당 점수가 기준 미만인지 확인합니다. 범위를 벗어난 위치를 먼저 읽으면 빈 목록과 종료 처리가 안전하지 않습니다. `if` 한 번으로는 연속된 불일치 기록을 모두 건너뛰지 못합니다.

`next`의 순서는 **끝 확인 → 반환할 값 복사 → 위치 증가 → 다음 일치 위치 탐색 → 복사한 값 반환**입니다. 반환하기 전에 인덱스를 바꿨다는 이유로 새 위치의 값을 반환하지 않도록 주의합니다. 종료에는 `std::nullopt`를 사용합니다.

`createIterator`는 생성 함수입니다. `std::make_unique<ScoreIterator>`로 구체 객체를 만들고 `std::unique_ptr<SubmissionIterator>`로 반환할 수 있습니다. 제공된 생성자는 벡터를 값으로 받습니다. 원본을 전달하면 복사본이 만들어집니다. 그 복사본을 Iterator 내부로 옮기는 것과 원본 목록 자체를 이동시켜 비우는 것은 다릅니다.

스냅샷 복사는 원본 기록 수에 비례하는 시간·공간이 듭니다. 두 슬롯과 최대 200개 명령인 이 실습에서는 명확한 수명과 변경 규칙을 위해 이 비용을 허용합니다. 실서비스나 STL의 모든 Iterator가 이 방법을 사용한다는 의미는 아닙니다.

## I1 등록 순서와 값 보존

1. 목록이 기록을 뒤에 추가하는지, Iterator가 인덱스 증가 방향으로 읽는지 확인합니다. ID나 점수로 정렬하면 안 됩니다.
2. 점수가 서로 다르고 ID 사전순이 뒤섞인 기록 3개를 추가합니다. `OPEN A 0` 뒤 `NEXT A`를 반복해 추가한 순서 그대로 ID와 점수가 나오는지 확인합니다.
3. 같은 점수인 서로 다른 ID도 모두 반환해야 합니다. 중복 제거 기준을 점수로 바꾸지 않습니다. `next()`는 한 기록의 ID와 점수를 함께 복사합니다.

## I2 필터와 같은 점수 포함

1. 유효 조건은 `score >= minScore_`입니다. 건너뛰는 조건은 그 반대인 `score < minScore_`입니다. 기준과 같은 점수를 건너뛰지 않습니다.
2. 점수 10, 70, 20, 30, 90의 순서로 기록을 추가하고 기준 70으로 엽니다. 반환되는 점수는 70, 90 순서입니다.
3. 생성 시와 다음 기록으로 이동할 때 모두 필터를 적용합니다. 첫 위치만 검사하거나 불일치를 한 개만 건너뛰는 구현은 중간의 연속 불일치에서 틀립니다.

## I3 조회가 기록을 소비하지 않음

1. `hasNext() const`는 위치를 바꾸지 않습니다. 내부에서 `next()`를 호출하거나 조회 횟수만큼 위치를 증가시키지 않습니다.
2. 일치 기록 2개를 만들고 `HAS A`를 세 번 호출한 뒤 `NEXT A`를 실행합니다. 여전히 첫 기록이 나와야 합니다.
3. 첫 `NEXT` 뒤에도 같은 방식으로 점검합니다. 모든 기록을 소모한 뒤에는 반복 `HAS A`가 계속 `HAS 0`이어야 합니다. 매번 1을 반환하는 임시 구현도 제거합니다.

## I4 한 건씩 전진과 반복 종료

1. `next()`가 반환할 현재 기록을 먼저 보관하는지 확인합니다. 인덱스 증가가 빠지면 같은 기록이 반복되고, 두 번 증가하면 한 기록을 누락합니다.
2. 일치 기록 2개를 연 뒤 `NEXT`를 다섯 번 실행합니다. 기록 2개 이후 세 번은 모두 `END`입니다.
3. 종료 상태에서는 벡터에 접근하지 않고 빈 optional을 반환합니다. 종료 직후 위치를 0으로 돌리거나 마지막 값을 재사용하지 않습니다. 처음으로 돌아가는 것은 `RESET`의 책임입니다.

## I5 두 Iterator의 독립성

1. `position_`와 `minScore_`가 Iterator의 일반 멤버인지 확인합니다. `static` 멤버나 전역 값이면 두 슬롯이 공유할 수 있습니다.
2. 점수 30, 80, 95를 등록하고 `A`는 0, `B`는 80으로 엽니다. `NEXT A` → `NEXT B` → `NEXT A`의 점수는 30 → 80 → 80입니다.
3. A와 B는 서로 다른 객체여야 합니다. 같은 객체 포인터를 두 슬롯에 넣거나 생성 때 기존 Iterator를 돌려주지 않습니다. `RESET A`가 B의 위치를 바꾸는지도 함께 확인합니다.

## I6 추가 후 스냅샷 유지

1. `OPEN` 직후 새 기록을 원본에 추가합니다. 기존 Iterator는 그 기록을 볼 수 없어야 합니다.
2. 40점 기록을 등록하고 A를 연 뒤 90점 기록을 추가합니다. A가 읽을 수 있는 기록은 1개입니다. 그 뒤 새로 연 B는 2개를 읽습니다.
3. `ScoreIterator`가 원본 벡터의 참조·주소나 STL 반복자를 저장하지 않는지 확인합니다. 원본에 대한 `const` 참조도 스냅샷이 아닙니다. 다른 경로의 `ADD`는 그 참조가 가리키는 원본을 바꿀 수 있습니다.

## I7 원본 삭제와 ID 재사용

1. `CLEAR`는 `SubmissionLog`의 원본만 비웁니다. 이미 열린 Iterator는 자신의 복사본으로 계속 순회합니다.
2. `s01 30`을 추가하고 A를 연 뒤 `CLEAR` → `ADD s01 90` → `OPEN B 0`을 실행합니다. A는 30, B는 90을 읽어야 합니다.
3. 원본 삭제가 Iterator를 닫거나 위치를 바꾸지 않도록 합니다. 복사본에 ID만 보관하고 `next`에서 현재 원본의 점수를 다시 찾는 방식도 안 됩니다. ID와 점수를 함께 복사합니다.

## I8 빈 목록과 일치 항목 없음

1. 빈 원본에 `OPEN A 0`은 성공합니다. Iterator 자체가 없는 상태와 Iterator는 있지만 결과가 없는 상태를 구분합니다.
2. 빈 목록을 연 후 `HAS`, `NEXT`, `RESET`, `NEXT`의 출력은 각각 `HAS 0`, `END`, `OK RESET`, `END`입니다.
3. 원본에 20점 기록을 추가하고 기준 90으로 다시 열어 같은 종료 동작인지 확인합니다. 필터 탐색이 끝까지 진행되면 위치를 크기와 같게 유지합니다. 마지막 원소로 되돌리지 않습니다.

## I9 같은 스냅샷으로 초기화

1. `reset()`은 위치만 0으로 되돌린 뒤 필터 탐색을 다시 실행합니다. 기존 기준 점수와 스냅샷은 유지합니다.
2. 20, 80점 기록을 넣고 기준 70으로 A를 엽니다. 첫 기록을 읽은 뒤 `RESET A` → `NEXT A`에서 다시 80이 나와야 합니다. 20이면 첫 위치의 필터 적용이 빠진 것입니다.
3. 원본에 100점을 추가해도 A의 `RESET`에는 반영하지 않습니다. 종료 전과 종료 후 모두 초기화해 보세요. 새 원본이 필요하면 `RESET`이 아니라 `OPEN`을 사용합니다.

## I10 한 슬롯만 교체

1. 같은 슬롯의 `OPEN`은 이전 Iterator 객체를 새 객체로 교체합니다. 기준 점수만 바꾸고 이전 위치를 유지하지 않습니다.
2. A와 B를 모두 연 뒤 한 건씩 읽고 원본에 기록을 추가합니다. A만 다시 연 다음 A가 새 목록의 첫 일치 기록부터 읽는지 확인합니다.
3. B의 다음 기록은 재생성 이전의 위치에서 나와야 합니다. 슬롯을 고른 뒤 그 슬롯 하나의 소유 포인터만 교체하는 제공 흐름을 유지합니다. 실패한 `OPEN`은 I12와 같이 아무 슬롯도 교체하지 않습니다.

## I11 점수 경계

1. 점수 0, 50, 100을 추가합니다. 기준 0이면 세 기록 모두, 기준 100이면 마지막 기록만 반환합니다.
2. `>=`와 범위 검증에서 양 끝값을 빼지 않았는지 확인합니다. 기준 100을 특별한 종료 신호로 사용하지 않습니다.
3. 0점인 기록은 유효한 `Submission`입니다. optional의 값 존재 여부와 기록의 점수가 0인지 여부를 혼동하지 않습니다.

## I12 오류 우선순위와 상태 보존

1. 제공된 검증 순서를 유지합니다. `ADD`는 점수→중복, `OPEN`은 슬롯→기준 점수, 조회·반환·초기화는 슬롯→열림 여부입니다.
2. A를 열고 한 건 읽은 뒤 `OPEN A -1`을 시도합니다. `ERROR score` 뒤 `NEXT A`는 기존의 두 번째 일치 기록이어야 합니다. 기존 Iterator를 먼저 지운 뒤 입력을 검사하면 안 됩니다.
3. 이미 있는 ID에 범위 밖 점수를 주면 `ERROR score`, 유효한 점수로 다시 추가하면 `ERROR duplicate`입니다. 두 오류 모두 원본 크기·기록을 바꾸지 않습니다.
4. 소문자 `a`와 미지원 슬롯은 `ERROR slot`입니다. 아직 열지 않은 유효 슬롯의 `HAS`, `NEXT`, `RESET`은 `ERROR unopened`입니다. 잘못된 슬롯을 A로 간주하는 기본 분기를 만들지 않습니다.

## 실패 결과를 읽는 순서

1. 컴파일 실패라면 해당 오류부터 해결합니다. 기능이 미검사인 상태를 기능 구현 실패로 해석하지 않습니다.
2. `ERROR incomplete`가 보이면 호출된 TODO를 먼저 완성합니다. 생성자에서 호출되는 보조 함수도 포함합니다.
3. I1~I4가 함께 실패하면 생성·필터·반환의 공통 흐름을 확인합니다. I5~I10 위주로 실패하면 스냅샷 소유권과 위치의 수명을 확인합니다.
4. I11~I12만 실패하면 경계·검증·오류 뒤 상태를 확인합니다. 한 번의 명령이 아니라 그 뒤 정상 명령까지 비교합니다.
5. 기능을 통과한 뒤에도 Iterator 인터페이스로 위임했는지, 클라이언트가 저장소를 직접 순회하지 않는지 코드로 확인합니다.

# 학생별 제출 이력·점수 변화·코드 비교 (0.5.4)

2026-09-17 구현. 직접 파일 제출(bundle) 방식이 대상이다. GitHub 커밋 기반 구형 제출의
중복 처리 정책은 변경하지 않았다. 실제 운영 서버 배포·학생 데이터 변경은 수행하지 않았다.

## 관리자 사용 방법

1. 수업 → **학생별 결과·코드 확인**에서 학생의 **코드·제출 이력 확인**을 연다.
2. **이 학생의 동일 과제 제출 이력**에서 제출 순번, 서버 접수 시각(UTC), 제출 묶음 SHA-256,
   점수, 직전 대비 증감, 상태를 확인한다. 큰 화면은 표, 작은 화면은 카드로 표시된다.
3. **#번호 제출**을 누르면 그 제출 당시 원본 코드와 점수를 연다.
4. **직전 제출과 코드 비교**를 누르고 파일을 선택하면 추가·삭제·수정된 내용을 확인한다.
   비교 화면에는 두 접수번호·시각·점수·증감이 함께 표시된다. `−`는 이전 코드, `+`는 현재 코드다.
5. 100건을 넘으면 **이전 제출 100건 / 더 최근 제출 100건**으로 이동한다.
   페이지 경계의 증감도 전체 접수 순서를 기준으로 계산한다.

순번은 현재 보관된 동일 학생·동일 과제 릴리스의 접수 순서다. 영구 식별자는 접수번호와 SHA-256이다.
같은 소스도 새로 제출하면 별도 순번을 갖고 동일 해시를 공유할 수 있다.
SHA-256은 제출 아카이브 전체의 식별값이며 Git 커밋 번호가 아니다.
파일별 비교는 포함된 파일의 해시와 검증된 내용을 사용한다.

## 점수 해석

- **이번 점수:** 선택하거나 새로 제출한 접수번호의 결과. 이전 점수로 대체하지 않는다.
- **직전 대비 증감:** 바로 이전 접수와 두 점수가 확정되어 있고 배점이 같을 때만 계산한다.
  미채점·처리 실패·배점 변경은 0점으로 환산하지 않고 `—`로 표시한다.
- **이전 최고점:** 선택한 제출보다 먼저 접수된, 같은 학생·같은 과제 릴리스의 **공개 완료된 결과** 중 최고점.
  현재 제출이나 더 나중 제출은 포함하지 않는다. 동점이면 더 최근 접수를 표시한다.
- 관리자 이력은 기존 교수자 권한대로 공개 전 채점 점수도 볼 수 있다. 학생 API의 이전 최고점은
  공개 점수만 포함하며 비공개 채점 항목·데이터를 제공하지 않는다.
- 이 기능은 점수 추적용이다. 최고점이 최종 성적이라는 새 평가 정책을 설정하지 않는다.
  코드 변경이 점수 변화의 원인인지를 자동 판정하지도 않는다.

## 재제출과 재전송 구분

| 상황 | 0.5.4 동작 |
| --- | --- |
| 접수 성공 후 학생이 다시 제출 | 같은 파일이어도 새 요청 키·접수번호·시각으로 접수하고 별도 채점 |
| 응답 유실로 같은 요청을 재전송 | 같은 요청 키를 사용하여 기존 접수번호 반환, 중복 접수 안 함 |
| 같은 요청 키로 다른 파일 전송 | 충돌로 거절 |
| A → B → A 제출 | 3개 접수 기록, 세 번째가 최신. 파일 저장소는 동일 A 데이터를 공유할 수 있음 |

Visual Studio의 성공 응답 캐시는 제거했다. 미확인 요청의 키만 메모리에 보관하고 성공 시 지운다.
학생이 다시 누르는 제출은 새 요청이며, 작업 중 중복 클릭은 기존 버튼 비활성화로 차단한다.
VS Code는 기존 미확인 요청 키 관리 방식을 유지한다. 접수 후 결과 패널을 현재 번호로 전환하며,
**최신 결과**를 누르면 메모리 속 과제 목록 대신 서버에서 최신 번호를 다시 확인한다.
로그아웃·IDE 종료 후 미확인 요청 키를 복원하지 않으므로 응답이 불명확할 때는 기록부터 확인한다.

새 제출은 내용이 같아도 기존 일일 제출·동시 대기 한도를 사용한다. 기본 한도(하루 50회·대기 3건)는
늘리지 않았다. 과거 버전에서 합쳐진 제출 클릭의 시각·횟수는 소급 복원할 수 없다.
서버의 접수 시각이 같은 경우 DB 삽입 순서로 정렬해 임의의 접수번호 정렬로 최신이 바뀌지 않게 했다.

## 코드 비교 안전 범위

- 교수자 인증 후 두 제출의 수업·학생·과제 범위를 확인한다. 다른 학생·과제의 조합은 거절한다.
- 원본을 실행·압축 해제·수정하지 않는다. HTML·제어문자·방향 전환 문자는 안전하게 표시한다.
- 파일별 SHA-256 검증 후 읽고, 파일당 256 KiB·1,000줄까지 비교한다. 출력은 256 KiB로 제한한다.
- 바이너리·UTF-8이 아닌 파일·한도 초과는 생략 안내를 표시한다. 파일 목록은 200개씩 이동한다.
- 줄바꿈·UTF-8 BOM은 정규화하므로 바이트 차이가 있어도 텍스트 차이는 없을 수 있다.
- 원본 손상·누락은 오류로 표시하며 임의의 다른 버전으로 대체하지 않는다.

## 배포·현장 확인

1. 데이터 백업 후 새 서버 코드를 설치하고 기존 방식으로 재시작한다. 이 변경 자체는 DB 스키마를 추가하지 않는다.
   이전 다운로드 진단 버전까지 함께 업데이트한다면 해당 버전의 schema 12 안내를 따른다.
2. Visual Studio와 VS Code 확장을 **0.5.4**로 업데이트한다. 구 Visual Studio는 성공 캐시가 남아
   서버를 업데이트해도 동일 파일을 새로 전송하지 않을 수 있으므로 함께 업데이트해야 한다.
3. VS Code는 생성된 0.5.4 VSIX를 시험 설치한다. Visual Studio는 Windows에서
   `extensions\visualstudio\build.ps1`로 빌드·설치한다. macOS 컴파일만으로 Windows VSIX 설치를 검증한 것은 아니다.
4. 시험 계정으로 A 제출·채점 → B 수정 제출·채점 → A 재제출을 한다. 모두 저장한 뒤 제출한다.
   세 접수번호가 다르고 마지막이 최신인지, 최고점은 별도로 표시되는지 확인한다.
5. 관리자에서 점수 증감과 코드 비교, 모바일 화면을 확인한다. 학생 토큰으로 관리자 주소는 열리지 않아야 한다.

## 재현 가능한 시험

`tests/integration/test_submission_timeline.py`는 실제 SQLite·HTTP와 합성 점수를 사용해
A/B/A, 동일 시각 정렬, 미공개 점수 차단, 다른 학생·수업 차단, 102건 페이지 경계,
동시 재전송, 파일 비교 크기·인코딩 제한을 검사한다. 컴파일 채점 자체는 기존 별도 시험에서 다룬다.

브라우저 검사:

```text
.venv/bin/python -m pytest -q tests/integration/test_submission_timeline.py --basetemp=<새 테스트 전용 임시 디렉터리>
node scripts/check_submission_timeline.cjs <같은 디렉터리> <playwright 모듈 경로> [Chrome 실행 파일]
```

pytest는 `--basetemp`를 비우므로 운영 데이터·작업 디렉터리를 지정하면 안 된다.
합성 화면의 모바일·태블릿·데스크톱/밝음·어두움 32개 조합을 검사한다.
실제 Windows IDE·iOS Safari/Android 기기와 운영 HTTPS 환경은 별도 현장 검증이 필요하다.

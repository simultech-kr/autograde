# Autograde Next.js 전환 계획

2026년 10월 10일 보완한 전환 계획입니다. Next.js로 웹 화면을 단계적으로 전환하고, 기존 Python의 인증·권한·과제·제출·채점 서비스와 SQLite를 유지합니다. 첫 전환 대상은 교수자의 제출·채점 현황 조회입니다. 쓰기 작업과 학생 인증 화면은 조회 화면의 검증 이후에 이전합니다.

목표는 화면 일관성, 반응형 사용성, 결과 갱신 비용과 기능별 유지보수성을 개선하는 것입니다. 프레임워크 교체 자체를 채점 성능 향상이나 일반 학생 코드의 안전한 실행으로 간주하지 않습니다. 0~2단계 구현은 별도 읽기 API와 웹 프로젝트에 한정하며 운영 서버 배포·DB 변경·IDE 변경은 포함하지 않습니다.

## 핵심 결정

| 항목 | 결정 |
| --- | --- |
| 웹 프런트엔드 | Next.js App Router와 TypeScript로 별도 `web/` 프로젝트 구성 |
| 서버 | Python 서비스를 유지하고 웹 전용 JSON 어댑터를 추가 |
| 데이터 | Python만 SQLite와 제출·채점 파일에 접근. Next.js의 직접 DB 접근 금지 |
| 도입 방식 | 같은 도메인의 `/app`에서 새 화면을 병행 제공하고 기능별로 전환 |
| 첫 출시 단위 | 담당 수업 선택과 제출·채점 현황 읽기. 상세·수정은 기존 화면 연결 |
| 디자인 | 기존 의미 기반 색상 토큰을 CSS Modules와 공통 React 컴포넌트로 이전 |
| 인증 | 1차는 기존 Python Basic 인증 유지. CSRF 쿠키를 로그인 세션으로 오인하지 않음 |
| 파일 전송 | 브라우저에서 Python 업로드 경로로 직접 전송. Next.js에서 ZIP 중계하지 않음 |
| 제품 구성 | 기능별 UI 모듈과 서버 capability 계약. SES 규칙을 프런트엔드에 복제하지 않음 |
| 운영 | 자체 서버와 Nginx 유지. Node 프로세스는 내부 전용. Docker·Vercel·NestJS 필수 도입 없음 |

Bootstrap은 기존 화면을 빠르게 정리하는 대안이지만 이번 전환의 필수 의존성으로 추가하지 않습니다. Bootstrap과 별도 UI 프레임워크를 중복 도입하지 않고, 공통 컴포넌트의 키보드·테마·모바일 계약부터 고정합니다. 복잡한 접근성 컴포넌트에 외부 라이브러리가 필요하면 첫 화면 시제품에서 하나를 선정하고 라이선스와 의존성을 검토합니다.

## 배포 구조와 주소

외부 주소와 IDE 접속 설정은 유지합니다. 다음 내부 포트는 저장소의 [Nginx 예제](../../config/nginx-autograde-portal.conf.example)를 기준으로 한 목표 구성이며, 실제 서버의 사용 중인 포트와 방화벽은 도입 전에 확인합니다.

| 외부 요청 | 처리 대상 | 상태 |
| --- | --- | --- |
| `https://ai.cbchoi.info:20010/app/...` | 새 Next.js, 내부 `127.0.0.1:18082` 후보 | 신규 |
| `/app/_next/...` | Next.js 정적 자산 | 신규 |
| `/instructor/api/v1/...` | Python 웹 서버 `127.0.0.1:18081` | 신규 JSON 계약 |
| 기존 `/instructor`, `/courses/...` | 기존 Python 웹 화면과 동작 | 유지 |
| 기존 교수자 ZIP·CSV 업로드와 파일 다운로드 | Nginx에서 Python 웹 서버로 직접 전달 | 유지 |
| `/instructor/api/v1/` 아래 ZIP·CSV·다운로드 별칭 | 동일 Python 검증·파일 처리에 연결 | 해당 화면 전환 시 신규 |
| `https://ai.cbchoi.info:20000/v1/...` | 기존 Python API `127.0.0.1:18080` | IDE 계약 유지 |

Next.js는 `basePath=/app`로 빌드합니다. `/app`과 정적 자산 경로만 새 프로세스에 연결하고, 기존 `/courses/.../instructor` 전체를 Next.js로 넘기지 않습니다. 같은 접두사 아래 있는 POST·업로드·다운로드까지 가로채는 것을 방지합니다. 최종적으로도 기존 GET 진입 주소에서 새 화면으로 이동시킬 수 있으며 외부 URL 전체를 재설계할 필요는 없습니다.

외부에 18082를 개방하지 않습니다. 자체 호스팅에서는 Next.js 앞에 Nginx 같은 역방향 프록시를 두는 구성을 공식 문서도 권장합니다. [Next.js 자체 호스팅](https://nextjs.org/docs/app/guides/self-hosting)

20010과 20000은 같은 호스트여도 서로 다른 origin입니다. 새 웹 브라우저가 IDE API로 직접 교차 출처 요청을 보내는 구조로 바꾸지 않습니다. 반대로 쿠키는 포트로 분리되지 않으므로 포트만으로 인증 경계를 보장하지 않습니다.

## 인증과 데이터 보호

### 교수자 인증을 먼저 검증

현재 `autograde_instructor_web`은 `Path=/`, HttpOnly, SameSite=Strict인 서명된 CSRF 쿠키입니다. 개인 인증 모드에서는 Basic으로 인증한 principal에 결합됩니다. 이 쿠키가 있다는 이유만으로 로그인하거나 담당 수업을 추정하지 않습니다. 공유 모드와 개인 모드를 구분하며, 개인 계정의 비활성화·비밀번호 변경·분반 권한 회수는 Python에서 계속 검사합니다.

1차 인증 흐름과 신규 읽기 API 계약은 다음과 같습니다. 기본 설정에서는 비활성화하고 명시한 시험 수업만 허용합니다.

1. Next.js는 개인 데이터 없는 공통 화면과 인증 안내를 제공합니다.
2. 교수자는 Python의 `/instructor/api/v1/entry`로 최상위 페이지 이동하여 기존 Basic 인증을 수행합니다. 설정된 공유·개인 인증 서비스의 기존 realm과 `WWW-Authenticate`를 그대로 사용합니다. Python이 CSRF 쿠키를 설정한 뒤 허용된 `/app` 화면으로 이동시킵니다. entry와 303 응답도 `no-store`로 처리합니다.
3. 복귀 주소는 임의 URL이 아니라 서버가 허용한 화면 키와 검증한 수업 ID로 구성합니다. 인증 진입과 이후 API를 같은 `/instructor/api/v1/` 아래에 두어 Basic 보호 영역의 재사용을 시험합니다.
4. 브라우저는 같은 origin의 `/instructor/api/v1/bootstrap`에서 사용자·담당 수업·CSRF·허용 기능을 받습니다. 비밀번호나 Basic Authorization 문자열을 JavaScript로 수집·저장하지 않습니다.
5. 이후 조회·변경은 브라우저에서 Python 웹 API로 직접 요청합니다. Python이 매 요청 인증·분반 권한을 재검사하고, 변경 요청은 Origin과 CSRF도 검증합니다.
6. 401에서는 자동 재시도를 중단하고 명시적인 재인증 이동을 제공합니다. 403을 로그인 성공이나 빈 데이터로 처리하지 않습니다. CSRF 오류는 권한 거절과 구분하여 제한된 bootstrap 재조회로 안내하되 변경 요청을 자동 재실행하지 않습니다.

Basic 인증 재사용·challenge·재인증은 Chrome, Edge, Safari의 새 프로필에서 검증해야 하는 선행 조건입니다. 동작하지 않으면 비밀번호를 브라우저 저장소에 넣는 우회 없이 전환을 중단합니다. Basic 인증은 명확한 로그아웃·계정 전환 UX에 제약이 있습니다. CSRF 쿠키를 지워도 브라우저의 인증 캐시는 삭제되지 않으므로 인증 해제에 성공한 것처럼 표시하지 않습니다. 공용 교수자 PC에는 브라우저 종료 안내 등 기존 제약을 표시합니다.

1차의 Server Components는 공통 레이아웃 등 비민감 내용을 담당하고, 인증 데이터는 Client Components에서 Python API를 통해 조회합니다. Next.js의 기본 서버 컴포넌트와 상호작용용 클라이언트 컴포넌트를 역할에 따라 구분합니다. 인증 데이터의 SSR을 처음부터 강제하지 않습니다. [서버와 클라이언트 컴포넌트](https://nextjs.org/docs/app/getting-started/server-and-client-components)

명확한 로그인·로그아웃이나 인증 데이터 SSR이 필요하면 후속 별도 변경으로 **Python 소유의 회수 가능한 교수자 세션**을 설계합니다. 기존 CSRF 쿠키를 재해석하거나 Next.js에 두 번째 사용자 DB를 만들지 않습니다. 그때도 Next 서버의 Python 호출은 허용된 내부 주소로만 제한하고 필요한 인증 헤더만 전달하며 사용자별 응답을 공유 캐시하지 않습니다.

### 학생 인증과 공용 PC

학생 웹은 기능별 전환까지 기존 경로를 유지합니다. 2026-10-29 공용 PC 보완 이후 공통 회원·수업별 인증 쿠키는 `Path=/`, 가입·로그인 전용 CSRF 쿠키는 `Path=/student`입니다. 수업별 인증도 계정 전환 경로에 전달되어 이전 학생의 서버 세션을 폐기할 수 있어야 합니다. 유효기간은 10분이며 세션 상태는 Python 메모리에 있습니다. 서버 재시작·여러 웹 프로세스 사이에서 자동 공유된다고 가정하지 않습니다.

학생 화면을 `/app`으로 옮길 경우 인증·권한은 계속 Python이 소유합니다. 초기 방식은 비민감 화면 셸과 같은 출처의 브라우저 API 조회입니다. 현재 Nginx는 `/app` 요청의 Cookie·Authorization을 제거하므로 쿠키가 `Path=/`라는 이유로 Next.js가 인증 정보를 받아 SSR할 수 있다고 가정하지 않습니다. API는 매 요청마다 계정과 수강 권한을 확인하며 쿠키 경로를 권한 경계로 사용하지 않습니다. 기존 학번·개별 비밀번호·수령 코드와 IDE 인증 계약을 유지합니다. QR코드는 다시 도입하지 않습니다.

`/app/preview/portal`은 예시 데이터를 사용하는 디자인 시안으로 유지합니다. 실제 학생 화면은 `/app/student`이며, `/student/api/*`를 통해 Python의 공통 회원 인증·수강 목록·수강 신청·본인 확인·비밀번호 복구를 사용합니다. 가입과 수강 선택은 분리하며, 신규 계정은 교수자가 본인을 확인해 발급한 일회용 코드로 활성화해야 합니다. 기존 학생은 수업 비밀번호 인증 후 공통 계정을 연결할 수 있습니다. 자료·시험지는 같은 출처의 기존 인증된 목록과 다운로드 경로를 사용합니다. 운영 설정은 [학생 포털과 IDE 사용성](../operations/student-portal-next.md)을 참고합니다.

### 공통 보호 기준

- 학번·점수·제출 코드·수령 코드·CSRF가 포함된 HTML과 JSON은 `Cache-Control: no-store`로 취급합니다. 서비스 워커·localStorage·브라우저 영구 query cache에 저장하지 않습니다.
- 수업 전환·계정 변경·권한 오류 시 이전 데이터와 진행 중 요청을 폐기합니다. URL에는 인증 정보와 학생 비밀번호를 넣지 않습니다.
- Next.js 클라이언트 번들·공개 설정에 서버 비밀키, 교수자 공용 토큰, 채점 원본을 넣지 않습니다. 선택한 교과목 ID 자체는 인가 증거가 아닙니다.
- 변경 요청의 원래 Origin을 검사합니다. Nginx가 잘못된 Origin을 정상값으로 덮어쓰지 않습니다. GET으로 저장·검증·공개·삭제를 실행하지 않습니다.
- 권한 있는 요청만 최소 필드 DTO를 받습니다. 학생용 결과와 교수자 비공개 결과를 같은 DTO로 무분별하게 공유하지 않습니다.
- 새 Route Handler가 추가되더라도 공개 API와 같은 수준으로 인증·인가합니다. UI에서 버튼을 숨기는 것으로 대체하지 않습니다. [Next.js 인증 안내](https://nextjs.org/docs/app/guides/authentication)
- 기존 Python CSP를 새 화면에 그대로 복사하면 Next.js 스크립트가 차단될 수 있습니다. 새 경로에 맞는 nonce 기반 CSP 등을 production build로 시험하고 기존 경로의 정책은 전역 완화하지 않습니다. 요청별 nonce를 사용하는 페이지는 동적 렌더링이 필요하므로 정적 HTML 공유 캐시의 이점을 동시에 얻는다고 가정하지 않습니다. 소스·문제 Markdown은 안전하게 렌더링하고 임의 HTML·MDX 실행은 금지합니다. [Next.js CSP 안내](https://nextjs.org/docs/app/guides/content-security-policy)

## 웹 API 계약

Python 서비스 호출을 감싸는 얇은 JSON 전달 계층을 추가합니다. 일반 HTML을 가져와 파싱하지 않습니다. 초기 API는 기존 서비스의 GET·POST 작업 의미를 유지하며, HTTP 메서드를 PATCH·DELETE로 바꾸는 REST 재설계는 필수로 하지 않습니다. 포털 라우터가 현재 허용하는 메서드와 JSON 본문 파싱을 명시적으로 확장·검증합니다.

### 신규 계약 묶음

| API 묶음 | 기능 | 우선순위 |
| --- | --- | --- |
| `/instructor/api/v1/entry`, `/bootstrap` | 인증 진입, CSRF, 담당 수업, 현재 기능 상태 | 선행 |
| `/instructor/api/v1/courses` | 역할에 맞는 교과목·분반 목록 | 선행 |
| `/instructor/api/v1/courses/{course}/results` | 과제·학생·상태 필터, 정렬, 페이지 조회 | 첫 화면 |
| 같은 수업 접두사의 `assignments`, `drafts`, `checks` | 과제 목록, 편집, 저장, 검증 상태, 공개 | 다음 단계 |
| 같은 수업 접두사의 `students`, `settings` | 개별 등록, 수강 관리, CSV 미리보기·적용, 수업 설정 | 다음 단계 |
| 같은 수업 접두사의 `submissions`, `rubrics` | 이력·코드·비교, 개인 교수자 평가 | 후속 |

0~2단계는 entry·bootstrap·courses·results만 구현하며 나머지는 후속 계약입니다. 기존 `/courses/{course}/instructor/checks/{job}/status`는 실제 JSON 조회이고, `submissions/live`는 JSON 안에 HTML을 담습니다. 기존 단일 서비스의 `/v1/instructor/dashboard`를 포털에 그대로 호출할 수 있다고 가정하지 않습니다.

### 응답과 변경 안전성

- 계약 버전, `request_id`, `course_key`, 서버 기준 시각, 허용 작업과 불가 사유를 명확하게 제공합니다. 오류는 안정적인 `code`, 안전한 `message`, 필요 시 필드별 오류를 갖습니다.
- 401 인증 필요, 403 권한·CSRF 거절, 404 접근 가능한 범위에 없음, 409 수정 충돌, 413 크기 초과, 429/503 재시도 가능 상태를 구분합니다. 기존 비노출 정책상 404를 쓰는 권한 경계는 유지합니다.
- 저장에는 기존 `revision`, 생성에는 기존 생성 키를 사용합니다. 추가로 멱등성이 필요한 공개·일괄 작업은 서버에서 요청 식별자를 처리한 뒤에만 재시도를 허용합니다. 브라우저가 임의로 POST를 자동 반복하지 않습니다.
- 업무 객체의 ID, 공개본 digest, 제출 ID, 이번 제출과 이전 최고점의 의미는 유지합니다. 기존·새 UI가 같은 서비스를 사용하며 DB 이중 쓰기·복제를 하지 않습니다.
- 학생 수, 제출 횟수, 완료한 학생 수를 분리합니다. 필터된 화면의 건수와 전체 집계의 범위를 명시합니다. 누락·미공개·처리 오류를 0점으로 변환하지 않습니다.
- 목록·집계·페이지를 같은 읽기 snapshot으로 제공합니다. 첫 페이지는 데이터셋 `version`을 반환하고, 후속 페이지와 주기 조회는 그 버전을 함께 보냅니다. 재제출·채점·수강 상태 변경 등으로 버전이 달라지면 `409 result_set_changed`로 거절하고 새 목록 알림을 표시합니다. 사용자가 반영하면 1페이지부터 다시 조회합니다. 결정적 정렬만으로 요청 사이의 중복·누락까지 막는다고 가정하지 않습니다. 이 계약은 0단계에서 고정합니다.

### ZIP과 CSV

브라우저의 FormData를 같은 origin의 Python multipart 경로로 보냅니다. 처음에는 기존 화면으로 최상위 이동하고, 편집 전환 단계에서 `/instructor/api/v1/courses/{course}/drafts/{draft}/uploads/...`와 `grading-template`, CSV 처리의 별칭을 추가합니다. 이 별칭은 기존 Python 인증 선행 검사·본문 제한·multipart 파서·서비스를 재사용하고 JSON으로 응답합니다. Nginx도 별칭 경로에만 대응하는 본문 한도를 적용합니다.

새 업로드 별칭은 기존 `proxy_request_buffering off`도 유지합니다. 본문 크기만 늘리면 Nginx가 전체 파일을 먼저 수신한 뒤 Python 인증을 호출할 수 있습니다. 실제 HTTPS 프록시를 거쳐 미인증·느린 업로드의 조기 거절을 시험합니다. 0~2단계의 API는 GET만 제공하며 업로드 크기 확대와 별칭 구현은 3단계까지 하지 않습니다. `^~` 접두사가 정규식 업로드 location을 무시하는 경우도 검증해야 합니다. [Nginx 요청 버퍼링](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_request_buffering)

이렇게 인증 entry와 업로드의 Basic 보호 영역을 맞춥니다. `/courses/...`의 기존 경로로 직접 파일을 보낸 뒤 중간 401 challenge와 파일 재전송이 성공하리라고 가정하지 않습니다. 별칭 준비 전까지는 파일 등록을 기존 Python 화면에서 수행합니다. 인증된 파일 다운로드도 새 UI에서 직접 사용할 때는 동일 보호 영역의 별칭을 제공하거나 기존 화면으로 이동합니다. 파일을 Base64로 감싸거나 Next Server Actions를 통해 이중 버퍼링하지 않습니다.

현재 ZIP 제한은 파일 5 MiB와 multipart 여유 64 KiB, CSV는 1 MiB와 여유 64 KiB이며 Nginx는 해당 경로에만 더 큰 본문을 허용합니다. 인증·수업 권한·Origin·CSRF 쿠키 사전 검사와 본문 처리 후 전체 CSRF 검사를 유지합니다. 새 JSON·설명·채점 케이스 경로의 본문 제한은 실제 최대 입력을 기준으로 별도 지정하여 기본 64 KiB 제한과 충돌하지 않게 합니다. 모든 경로를 일괄 무제한으로 열지 않습니다.

전송 진행과 서버 저장 완료, 검증 완료를 구분합니다. 네트워크가 끊기면 이미 저장된 자료·현재 revision을 다시 조회해 재선택 또는 재업로드 필요 여부를 안내합니다. 별칭 도입으로 기존 인가된 Python 경로를 제거하거나 파일 접근 권한을 완화하지 않습니다.

## 결과 화면과 성능 개선

우선 현재 API 처리 시간·SQL 시간·응답 크기·채점 큐 대기·실행 시간을 따로 측정합니다. Next.js가 줄이는 브라우저 렌더링 비용과 Python 조회 최적화의 효과를 분리합니다.

1. 수업·과제·제출 상태 필터와 페이지 크기 제한을 서버에 적용합니다. 전체 행을 받아 브라우저에서 숨기는 방식에서 벗어납니다.
2. 대시보드의 다운로드 진단을 `(student_key, assignment_id)`로 색인하여 행마다 전체 진단을 반복 탐색하지 않습니다. SQL은 수업 범위와 실행 계획을 확인한 뒤 수정하며 무조건 인덱스를 늘리지 않습니다.
3. 첫 버전은 현재 페이지의 제한된 JSON을 5초 간격으로 조회합니다. 5초는 인증 TTL을 갱신하는 근거가 아닙니다. 조회 중복 방지·탭 숨김/오프라인 중지·오류 백오프·작은 요청 시각 분산을 둡니다.
4. 페이지의 변경 버전과 데이터가 동일하면 화면을 다시 계산하지 않습니다. 안정적인 `course + student + assignment` 행 key를 사용하고 늦은 응답은 버립니다.
5. 다음 최적화로 변경 여부 확인 또는 delta 응답을 추가합니다. 접수뿐 아니라 채점 완료·결과 공개·학생 상태·과제 보관/삭제도 버전에 반영해야 합니다. 단순히 가장 최근 제출 시각만 비교하지 않습니다.
6. 정렬이나 필터에 영향을 주는 변경은 해당 페이지와 요약을 다시 조회합니다. 사라진 행 처리와 cursor 만료를 정의하기 전에는 무제한 delta 병합을 하지 않습니다.
7. 읽는 중인 행, 펼친 상세, 선택한 코드, 포커스와 스크롤을 보존합니다. 순위가 바뀌면 즉시 행을 이동시키기보다 새 결과 알림과 반영 동작을 제공합니다.

초기에는 SSE·WebSocket을 추가하지 않습니다. 현 Python HTTP 서버에는 동시 요청 제한이 있으므로 장시간 연결을 유지하는 방식은 별도 용량 설계가 필요합니다. Next 도입과 동시에 SQLite 교체·채점 워커 증설도 하지 않습니다. 측정으로 병목이 확인된 부분만 후속 변경합니다.

### 제안하는 성능 인수 기준

아래 숫자는 측정된 성능이 아니라 시험 목표입니다. CPU·메모리·브라우저·네트워크 조건과 기존 화면 기준치를 먼저 기록하고 같은 조건으로 비교합니다.

| 항목 | 목표 |
| --- | --- |
| 최소 동시 사용 | 합성 학생 25명의 인증·수령·제출·결과 확인과 교수자 2명의 현황 조회를 동시 수행 |
| 누적 데이터 | 4개 수업 분반 × 25명 × 10과제 × 5회 제출인 5,000개 제출로 목록·집계 시험 |
| 목록·상태 API | 채점 실행 시간과 업로드 전송을 제외한 p95 응답 500ms 이하 목표 |
| 화면 초기 표시 | 로그인 완료 상태에서 핵심 결과 표시 2초 이내 목표 |
| 결과 신선도 | 정상 연결과 전경 탭에서 서버 완료 후 10초 이내 새 결과 알림 목표. 목록 재정렬·점수 반영은 사용자의 명시적 갱신으로 수행 |
| 전송량 | 동일 필터·데이터에서 기존 전체 HTML 갱신 대비 평균 응답 바이트 50% 이상 절감 목표 |
| 안전성과 기존 성능 | 누락·중복 접수·분반 노출 0건, 기존 제출 접수 지연이 유의하게 악화되지 않음 |

동일 실습실 NAT에서 다수가 한 IP를 공유하는 조건도 시험합니다. 인증·조회 부하를 줄이려고 요청 제한이나 비밀번호 검증을 무조건 해제하지 않습니다. 목표를 만족하지 못하면 원인을 기록하고 해당 단계 공개를 보류합니다.

## 화면과 디자인 시스템

공통 화면은 학년도·학기·교과목·분반 문맥, 메뉴, 페이지 제목, 다음 행동, 연결 상태를 제공합니다. 수업 전환 시 이전 수업의 학생·과제 선택과 캐시를 해제합니다.

| 공통 구성 | 기준 |
| --- | --- |
| 수업 선택·탐색 | 담당 수업만 제공, 필터·검색·페이지는 URL로 복원 |
| 표·모바일 카드 | 320·375·768·1024·1440px에서 제목·점수·마감·대표 행동 식별 가능 |
| 상태와 점수 | 접수·대기·채점 중·완료·오류·미제출 분리, 이번 결과와 이전 최고점 분리 |
| 입력 폼 | 명시적 저장, 미저장 안내, 필드 오류, revision 충돌, 파일 재선택 필요 여부 |
| 위험 작업 | 대상·개수·영향·복원 가능성 확인. 개별 실패를 성공으로 합치지 않음 |
| 결과 갱신 | 마지막 성공 시각, 실패·재시도·새 결과 안내, 읽기 중 재정렬 보류 |
| 테마·접근성 | 밝음·어두움·고대비, 색상 외 상태 텍스트, 키보드, 포커스 복원, 움직임 감소 설정 |
| 시간 | 정확한 KST 시각과 시간대, 서버 기준 마감. 상대 시간은 보조 |
| 소스·문제 | 읽기 전용 코드, 안전한 Markdown, 코드·diff만 독립 가로 스크롤 |

교수자 과제 작성은 문제·학생 파일·채점 자료·검증·공개를 한 화면의 구획으로 유지합니다. 전환을 이유로 문제와 채점을 다시 별도 페이지로 분리하지 않습니다. 공개된 과제의 설명 수정과 채점 기준 변경은 기존 정책대로 구분합니다.

와이어프레임은 [기존 시안](../../design/prototypes/instructor-ux-wireframe.html)을 참고하되 현재 구현과 동일하다고 가정하지 않습니다. 먼저 새 결과 화면의 데스크톱·모바일·어두운 테마·오류 상태 시안을 확인한 뒤 실제 데이터 연결을 진행합니다.

## 모듈과 SES 제품 구성

새 웹은 `web/src/app`, `features`, `lib/api`, `lib/contracts`, `styles`, `web/tests`로 구성합니다. 0~2단계의 기능 registry와 결과 화면을 먼저 구현하고, 여러 기능에서 실제 재사용할 때 공통 컴포넌트를 분리합니다. 아직 구현하지 않은 기능의 빈 메뉴를 만들지 않습니다.

| 모듈 | 책임 |
| --- | --- |
| `features/courses` | 교과목·분반·수업 문맥 |
| `features/results` | 제출 현황, 필터, 갱신, 이번 결과와 최고점 |
| `features/assignments` | 과제 목록·작성·검증·공개·설명 갱신·보관·삭제 |
| `features/students` | 학생·수강·CSV·비밀번호 재설정 |
| `features/submissions` | 제출 시각·코드 버전·점수 변화·소스 비교 |
| `features/rubrics` | 기준 카탈로그와 교수자 전용 평가 |
| `features/student-portal` | 후속 학생 인증·과제 선택·코드 발급 |

공통 shell은 빌드에 포함한 신뢰 모듈의 `id`, 경로, 표시 이름, 필요한 capability를 registry에서 읽습니다. 서버 bootstrap은 사용자·수업에 허용된 기능과 준비 상태를 반환합니다. `edition === 'Pro'` 같은 상품명 조건으로 업무 규칙을 복제하거나 외부에서 임의 JavaScript를 다운로드하지 않습니다.

초기에는 기존 서비스 상태를 읽는 고정 capability 어댑터를 구현합니다. 전체 SES Host와 사용권 실행 엔진이 이미 있다는 의미가 아닙니다. 향후 [플러그인 설계](platform-plugin-ses.md)와 [SPL 설계](software-product-line.md)에 따라 선택·설치·호환성·사용권·사용자 권한·준비 상태의 교집합을 서버에서 계산합니다. 프런트엔드는 결과를 표현할 뿐 SES pruning을 독자 실행하지 않습니다.

기능을 꺼도 기존 제출 원본과 허용된 평가 이력은 보존합니다. 보고서·성취도·자동 압축 같은 미구현 기능을 메뉴만 만들어 운영 가능하다고 표시하지 않습니다. UI registry와 도메인 API 계약의 버전을 함께 관리합니다.

2026-10-10 현재 0~2단계의 로컬 코드는 구현했습니다. 합성 학생 25명·교수자 2명 동시 흐름, 5,000건 이력 조회, Chrome production 화면을 검증했습니다. 실제 Nginx/TLS·Edge/Safari·실습실 NAT·IDE 실기기 검증과 성능 인수 목표 전체는 아직 완료하지 않았으므로 **운영 공개 승인 대기** 상태입니다. 상세 수치·제외 조건은 [검증 기록](../testing/nextjs-pilot.md)을 기준으로 합니다.

실제 서버 사양·작업 인원·운영 시험 가능 시간을 확인한 뒤 단계별 기간을 산정합니다. 완료 날짜 대신 위 진입 조건으로 진행 여부를 결정합니다.

### 병렬 작업 경계

- Python 담당: API schema, 기존 서비스 어댑터, 인가·CSRF, 조회 성능, 계약 시험.
- 웹 담당: 공통 컴포넌트와 시안, 합의한 fixture로 화면 구현, 이후 실제 API 연결.
- 검증 담당: 기존 화면과 결과 비교, 브라우저·부하·권한·재제출·오류 복구 시험.
- 운영 담당: Nginx·Node 프로세스·TLS·본문 한도·로그·백업·롤백 리허설.

각 단계에서 API schema와 상태 의미를 먼저 합의하고 병렬 개발합니다. 같은 컨트롤러·DB schema를 여러 작업이 독립 수정하지 않습니다. 기능별 통합 후 회귀시험이 통과한 변경만 배포 후보로 묶습니다.

## 시험과 공개 승인

기존 Python 시험은 서버 정책의 회귀시험으로 유지합니다. 기존 화면이 공존하거나 롤백 경로로 남아 있는 동안 HTML·브라우저 시험도 함께 유지하고, 새 React 컴포넌트·실제 브라우저 시험을 추가합니다. 구 화면을 실제 제거할 때 해당 시험을 정리합니다. 기존 시험 통과를 새 Next.js 화면의 시험 통과로 기록하지 않습니다.

필수 시험은 다음과 같습니다.

1. 공유·개인 교수자 인증, 미인증, 잘못된 비밀번호, 비활성화, 담당 수업 회수, 타 수업·제출 ID 직접 요청.
2. Basic challenge 왕복, 만료·잘못된 CSRF, 다른 Origin과 `Origin:null`, 허용되지 않은 복귀 주소.
3. 2개 교수자 계정을 교대로 사용해 캐시·상태·화면에 다른 사용자의 정보가 남지 않는지 확인.
4. 409 충돌·저장 중 연결 끊김·중복 클릭·검증 중 수정·검증 후 변경·다른 탭에서 삭제.
5. 정상 ZIP, 경계 크기, 잘못된 ZIP, 경로 탈출, 큰 CSV, 동시·느린 업로드, 전송 중 인증 문제.
6. 접수·채점 대기·완료 구분, 재제출 현재 0점과 이전 최고점 100점, 미공개·미검사·실패 처리.
7. 제출·미제출 집계, 페이지 경계, 수업 전환 중 늦은 응답, 삭제된 필터 과제를 전체 과제로 자동 확대하지 않기.
8. 마감 직전·정각·직후와 업로드 중 마감, 연장·설명 갱신·공개본 정책 동일성.
9. 일괄 보관·삭제는 검토 후 대상 하나의 상태·revision이 바뀌거나 처리 불가이면 전체 적용을 거절하고 부분 변경을 남기지 않기. 일반 목록에서 삭제 항목 제외, 이력 보존·복원 권한 확인.
10. 학생 모바일 로그인·수령 코드·만료·재발급과 VS Code 및 Visual Studio 수락·다운로드·이어하기·제출·결과.
11. 밝음·어두움·고대비·키보드·화면 폭·긴 한국어·움직임 감소·갱신 중 포커스·스크롤 보존.
12. production CSP, 자산 로딩, 새로고침·직접 링크, Node 중단, Python 503, Nginx 경로와 구 화면 복귀.
13. 열어 둔 새 화면에서 CSV 기능 해제·시험 수업 제외 후 다음 API 요청이 거절되는지 확인. 동시에 구 화면과 학생 API는 유지하며, 변경된 목록 버전으로 다음 페이지 요청 시 중복된 행을 반환하지 않고 409로 거절.

재사용할 기준 시험은 `test_instructor_personal_auth.py`, `test_instructor_web.py`, `test_instructor_ux.py`, `test_instructor_assignment_bulk.py`, `test_instructor_assignment_deletion.py`, `test_instructor_submission_review.py`, `test_instructor_results_browser.py`, `test_student_portal_ux.py`와 기존 브라우저 검사입니다. 개발용 서버만이 아니라 production build와 실제 HTTPS 프록시를 거친 시험 결과를 남깁니다.

## 운영 설정과 롤백

Node·Next·React 버전은 구현 착수 시 지원되는 조합으로 확정하고 lockfile에 고정합니다. 자동으로 최신 버전으로 바꾸지 않습니다. 보안 업데이트와 의존성 검사는 운영 절차에 포함합니다. 지원 시스템 조건은 [Next.js 설치 안내](https://nextjs.org/docs/app/getting-started/installation)를 기준으로 확인합니다.

기존 Python CSV와 데이터 경로를 유지합니다. `instructor_next_results_enabled`는 기본 `false`이며, `true`일 때에는 `instructor_next_course_keys`에 세미콜론으로 구분한 시험 수업 목록이 필요합니다. 모든 신규 API 요청은 이 설정과 기존 분반 권한의 교집합을 검사합니다. CSV를 매 요청 다시 읽으므로 서버 재시작 없이 기능 해제·수업 제외가 반영되며, 파일 누락·오류에는 신규 API만 닫습니다. 데이터 경로·인증 방식·포트 변경을 실시간 적용하는 기능은 아닙니다. Node 실행 주소·포트는 실행 옵션과 비밀 없는 배포 설정으로 관리하며 운영자에게 환경변수 수동 선언을 강제하지 않습니다. 중첩된 제품 구성은 기존 SES 설계에 맞는 버전 있는 JSON으로 분리하고 브라우저에는 비밀을 제외한 허용 기능만 제공합니다.

배포 순서는 백업·복구 확인 → Python 추가 API 배포 → 내부 Next 프로세스 시작 → 상태 점검 → `/app` 연결 → 시험 수업 검증 → 기능별 기본 진입 변경입니다. 기존 UI와 신규 API를 함께 유지하는 기간에는 파괴적 DB 변경을 하지 않습니다.

문제가 생기면 먼저 CSV에서 `instructor_next_results_enabled,false`로 바꾸어 열린 탭의 신규 API까지 차단합니다. 이후 Next 진입 링크·리디렉션을 끄고 기존 Python 화면으로 복귀시킵니다. 링크만 숨기는 것은 롤백 완료가 아닙니다. 3단계의 쓰기 기능도 별도 서버 측 중단 설정 없이 공개하지 않습니다. 이미 처리 중인 요청을 취소하거나 DB를 과거 백업으로 되돌리지는 않습니다. 새 화면에서 접수한 작업은 같은 Python 원장에 있으므로 먼저 처리 결과와 작업 ID를 확인합니다. 쓰기 요청이 실패했다고 자동으로 구 서버에 재전송하지 않습니다.

Next 프로세스는 별도 상태 확인과 재시작 정책을 갖습니다. Node가 중단되어도 Nginx가 직접 구 화면 링크가 있는 503 안내를 제공하며 학생 API 요청을 다른 서버로 재전송하지 않습니다. 애플리케이션 오류에는 요청 ID를 제공하되 사용자 입력·쿠키·Authorization·수령 코드·소스를 로그에 남기지 않습니다. 배포 버전, 경로 템플릿, 상태 코드, 소요 시간 중심으로 관측합니다.

구 화면은 해당 기능의 동등성·운영 승인·복구 리허설을 통과하고 최소 한 번의 실습 운영을 마친 뒤에만 제거합니다. 롤백 가능한 빌드·정적 자산·설정은 함께 보존하여 열린 탭이 서로 다른 빌드의 자산을 섞지 않게 합니다.

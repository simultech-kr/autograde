# 교수자 서버 UI/UX 개선 계획

2026-09-18 · 전체 개선 계획. 현재 구현 범위는 아래 진행 상태와 운영 안내에서 구분한다.

진행: 단계 0의 상호작용 시안과 자동 검사를 작성했다.
[시안 범위·검토 순서·검사 결과](../testing/instructor-ux-wireframe.md)를 참고한다.
이후 교수자가 시안을 승인하여 P0 중심의 서버 1차 적용을 진행했다.
[구현 범위·업데이트·남은 단계](../operations/instructor-ux-update.md)를 참고한다.
P1 일부(단일 진입·수업 전환·통합 과제 조회)와 2차 편의 기능(미저장 경고·케이스 편집·검증 자동 조회)을 적용했다.
전체 로드맵 완료를 뜻하지 않으며, 아래 문제 분석은 최초 설계 시점의 기준이다.

## 1. 목표와 범위

교수자가 **수업·분반 선택 → 과제 준비·검증·공개 → 제출 현황 확인 → 학생 코드 검토 → 학기 정리**를
한 흐름으로 수행하도록 개선한다. 버튼 수를 늘리는 대신 현재 상태, 다음 행동, 실패 시 복구 방법을 명확히 한다.

이 문서는 현재 작업 트리의 구현을 기준으로 한다. 운영 서버에 같은 버전이 배포되었다고 가정하지 않는다.
기존 [과제 검증 6단계 UX](instructor-assignment-validation-ux.md),
[수업·학생 관리 설계](course-student-web-mvp.md)를 보완하며,
[SES 관리 모듈 설계](management-ses.md)의 보관·보고서·권한 정책을 대체하지 않는다.
Canvas/LTI, 시험 네트워크 통제, 확장 업데이트, Git 형태의 저장소 변경은 이번 UI 개선 범위에서 제외한다.

## 3. 정보 구조와 공통 화면

### 3.1 하나의 운영 홈, 고정된 수업 문맥

| 화면 | 우선 보여줄 내용 | 대표 행동 |
| --- | --- | --- |
| 전체 운영 홈 | 학기 필터, 교과목·분반 목록, 확인 필요한 작업 | 수업 선택 / 새 수업 등록 |
| 수업 개요 | 교과목명·코드·분반, 진행 과제, 접수·채점 현황, 마감 일정 | 진행 과제 열기 |
| 과제 | 통합 목록, 검증·공개 상태, 마감, 수락·제출 현황 | 새 과제 등록 |
| 학생 | 학번·이름·수강 상태, 검색, CSV 처리 결과 | 학생 등록 / CSV 등록 |
| 제출·결과 | 과제·학생·처리 상태 필터, 현재 제출 결과, 확인 필요 건 | 제출 이력·코드 열기 |
| 수업 설정 | 이름·학기·분반, 학생 접속 링크·QR, 수업 상태 | 설정 저장 |
| 보고서·보관 | 실행 모듈 제공 이후에만 노출 | 보고서 생성 / 보관 미리보기 |

- 상단에 `2026학년도 / 2학기 / come2201 · 교과목명 / 01분반`과 수업 전환을 둔다.
- 수업 전환 시 이전 수업의 학생·과제 선택을 해제한다. 동명의 과제를 자동 대응시키지 않는다.
- 현재 메뉴와 이동 경로를 표시하고 검색·필터·페이지를 URL로 보존한다. 인증 정보는 URL에 넣지 않는다.
- 기존 북마크와 CLI/확장 API는 유지한다. 기존 두 홈의 GET 주소를 새 홈으로 연결하되 POST 계약은 보존한다.
- 목록과 긴 등록 폼을 분리한다. 빈 목록에는 해당 문맥의 시작 행동 하나와 설명을 제공한다.
- 주요 행동은 화면별 하나, 보조 행동은 소수로 제한한다. 비활성화·숨김 등은 별도 위험 작업 영역에 둔다.

### 3.2 공통 시각·상호작용 규칙

- 기존 `web_theme.py`의 의미 기반 색상과 `instructor_responsive.py`를 재사용한다. 페이지마다 새 색상 체계를 만들지 않는다.
- 상태는 색상뿐 아니라 텍스트·아이콘으로 표시한다. 밝은 테마·어두운 테마·고대비에서 검토한다.
- 좁은 화면은 카드, 넓은 화면은 표로 제공한다. 코드·diff만 독립 가로 스크롤을 허용한다.
- 제목·점수·마감·대표 행동은 카드에서 바로 보이게 하고 긴 해시·진단은 펼쳐서 확인한다.
- 버튼은 줄바꿈되도록 배치하고 본문을 덮지 않는다. 키보드 포커스, 입력 라벨, 오류 연결, 상태 알림을 공통화한다.
- 연결 실패는 `0명`, `제출 없음`으로 바꾸지 않는다. 마지막 성공 기준 시각과 “현황 갱신 실패”를 표시한다.
- 학생·과제의 비신뢰 텍스트는 이스케이프한다. 토큰·비밀번호·비공개 채점 자료를 브라우저 영구 저장소에 보관하지 않는다.

## 4. 주요 업무별 개선

### 4.1 과제 목록과 상세

통합 조회는 **논리 과제, 공개 릴리스, 작성 초안**을 구분한다. 공개본과 그 초안을 동일 과제 두 건으로 집계하지 않는다.
CLI 등록 과제는 원본 출처를 표시하되 편집 가능한 것처럼 꾸미지 않는다.
서버가 계산한 `허용 작업 + 불가 사유`로 버튼을 구성하고, 실행 시 서버가 다시 검사한다.

목록 기본 정보는 제목·언어, 검증, 공개, 마감, 수락 학생 수·제출 학생 수다.
제출 건수는 재제출 포함 횟수이므로 학생 수와 별도 표기한다. 데이터가 없는 값은 0으로 추정하지 않는다.
검색과 상태 필터, 서버 페이지 나누기를 제공한다.

상태는 다음 축을 섞지 않는다.

- 검증: 미검증 / 대기 / 실행 중 / 성공 / 실패 / 중단 / 현재 버전 재검증 필요.
- 공개: 초안 / 예약 / 진행 / 마감 / 숨김 / 비활성. 보관은 실제 수명주기 기능 구현 후 추가한다.
- 제출별 처리: 접수 / 채점 대기 / 채점 중 / 완료 / 처리 오류. 결과 공개 여부는 별도 표시한다.

상세 상단에는 상태·마감·다음 행동을, 하단에는 `개요 / 준비·검증 / 제출·결과 / 운영 이력`을 배치한다.
공개 완료 이후 기본 화면을 편집용 마지막 단계가 아닌 운영 개요로 전환한다.
운영 이력의 개인별 행위자 표시는 개인 인증 구현 전까지 제공한다고 약속하지 않는다.

### 4.2 등록 → 검증 → 공개

기존 6단계를 유지한다: **문제 → 학생 파일 → 채점 자료 → 서버 검증 → 결과 확인·수정 → 공개**.

1. 진행 표시에서 완료·현재·차단 단계를 구분하고 차단 이유를 해당 단계 옆에 설명한다.
2. 명시적 저장을 우선 개선한다. 저장 완료 시각과 미저장을 표시하고 다른 단계·수업 이동 시 확인한다.
3. 입력 오류는 항목 아래에 설명하고 첫 오류로 포커스를 이동한다. 일반 입력은 유지하되 비밀번호는 재표시하지 않는다.
   파일 입력은 브라우저 제약상 다시 선택해야 할 수 있음을 안내한다. 이미 서버에 등록한 파일은 그대로 유지한다.
4. 채점 케이스는 추가·복제·삭제 방식으로 편집한다. 공개/비공개 구분, 배점 합계, 정답·오답의 기대 결과를 요약한다.
5. 검증은 서버 작업 ID로 추적한다. 대기·실행·종료 시각을 보여주고 보고되지 않은 세부 단계나 진행률은 만들지 않는다.
6. 조회는 예를 들어 5초 간격으로 시작하고 실패 시 간격을 늘린다. 완료·로그아웃·화면 이탈 시 중지하고 수동 갱신을 남긴다.
7. 공개 직전 수업·분반, 검증된 자료 버전, 학생용 파일, 배점, 공개 일정, 마감, 결과 공개 정책을 한 번에 검토한다.
8. 공개 완료 후 실제 공개 상태와 학생 수령 링크를 보여준다. 검증 성공만으로 공개 완료라고 표시하지 않는다.

자동 저장은 후속 선택 사항이다. 서버 revision 충돌 처리와 명확한 저장 상태를 갖춘 뒤 도입하며,
다른 탭의 변경을 덮어쓰거나 실행 중인 검증·공개본을 자동 수정하지 않는다.
현재 웹 등록은 C/C++ 단일 진입 파일·표준 입력/출력 채점 범위를 안내한다. 임의 Win32 프로젝트 채점을 지원한다고 표시하지 않는다.

### 4.3 마감과 과제 갱신

- 목록·상세·공개 확인에 정확한 마감과 `KST (UTC+09:00)`를 표시한다. 상대 시간만 표시하지 않는다.
- 서버 시각이 권한 판단의 기준이다. 화면 카운트다운은 보조 표시이며 재접속 시 갱신한다.
- 초안에 과거 마감을 입력하면 즉시 경고한다. 새 공개 시 이미 지난 마감의 일반 공개를 차단하는 서버 검증을 추가한다.
  과거 자료 이관이 필요하면 별도 명시적 운영 절차로 설계한다.
- 현재 마감 판정은 접수 기준이며 업로드 도중 마감을 넘으면 거절될 수 있다는 안내를 교수자에게 제공한다.
- 연장은 기존·새 마감, 사유, 대상 과제·분반, 영향을 확인한 뒤 실행한다.
- 현재 공개본은 기존 마감이 있는 경우에만 조건부 연장된다. 마감 단축, 무기한 과제의 마감 추가,
  학생별 유예는 별도 정책·서버 구현 전까지 버튼으로 제공하지 않는다.
- 공개본 자료 수정은 새 초안 복제·검증 방식이다. 기존 수락·제출 때문에 숨김/교체가 제한되면 그 이유를 표시한다.
  복제 버튼을 학생의 기존 제출을 새 버전으로 자동 이관하는 기능처럼 설명하지 않는다.

### 4.4 제출 현황 → 학생 이력 → 코드 비교

- 과제별로 미접수, 접수·채점 대기, 채점 중, 채점 완료, 처리 오류를 구분하고 목록 필터로 바로 연결한다.
- 학생 행에는 현재 접수 시각, 현재 상태·점수, 이전 공개 최고점, 이전 평가 대비 증감을 구분해 표시한다.
- 최근 접수가 채점 대기라면 과거 점수를 현재 점수로 표시하지 않는다. 미공개·자료 부족·서버 오류는 0점이 아니다.
- 학생 상세는 `제출 시각 → 접수 ID·코드 해시 → 점수 → 증감 → 비교`로 연결한다.
  비교 가능한 배점·기준인지 확인하고 비교 불가이면 이유를 표시한다.
- 코드 비교는 같은 학생·수업·릴리스 범위에서 기본 직전 제출을 선택하고, 다른 이력 선택도 허용한다.
  소스는 읽기 전용이며 화면에서 실행하지 않는다. 대용량 제한·파일 누락·비교 불가 상태를 설명한다.
- 기존 이력·diff를 재사용한다. 모바일에서는 별도 상세 페이지, 넓은 화면에서는 목록 문맥을 유지하는 상세 영역을 검토한다.
- 다운로드 장애·컴파일 오류·서버 오류를 분리한다. “확인 필요”를 부정행위나 학습 능력 판정으로 표현하지 않는다.

### 4.5 학생 관리와 학기 정리

- 학생 기본 정보와 이 수업의 수강 상태를 구분한다. 이름 변경이 다른 수업에도 반영되는 현재 동작을 저장 전에 알린다.
- 개별 등록과 CSV 등록을 분리하고 CSV는 미리보기 → 추가/변경/오류 확인 → 적용 순서를 유지한다.
- 비밀번호 재설정·수강 비활성화는 대상·범위·사유를 확인한다. 목록에 비밀번호를 표시하지 않는다.
- 학생 비활성화를 “영구 삭제”라고 부르지 않는다. 재활성화 가능 여부와 제출 이력 보존을 설명한다.
- 전체 초기화는 기존 오프라인 백업 절차로 안내한다. 일반 목록의 일괄 삭제 버튼으로 추가하지 않는다.
- 초안 삭제·과제 보관은 서버 기능을 갖춘 뒤 별도 제공한다. 진행 작업·공유 파일 참조·제출 이력 검사를 통과해야 한다.
- claim 종료나 제출 마감만으로 압축·삭제하지 않는다. 보관 미리보기 → 생성·검증 → 논리 보관 → 복원 순서를 따른다.
  이미 압축된 제출본을 다시 압축하는 것을 공간 회수의 보장으로 설명하지 않는다.

## 5. 모듈화와 구현 구조

현재 서버 렌더링과 SQLite를 유지한다. UI 개선을 위해 SPA 전환이나 DB 교체를 선행하지 않는다.

| 책임 | 개선 방향 |
| --- | --- |
| Controller | `instructor_web.py`의 인증·CSRF·입력·응답을 유지하며 수업/학생/과제/결과 단위로 점진 분리 |
| View | 공통 shell, 수업 선택, 상태 배지, 표/카드, 폼 오류, 확인 화면을 재사용 가능한 렌더러로 분리 |
| Query/View model | 통합 과제 목록, 상태 요약, 허용 작업·차단 이유, 집계 기준 시각을 읽기 전용 모델로 제공 |
| Service | 기존 `course_admin`, `assignment_admin`, `platform_state`, `submission_review`에 정책 유지. UI의 버튼 숨김으로 권한 검사를 대신하지 않음 |
| Repository | SQL은 조회/저장 책임에 모으고 페이지 단위 조회. 카드마다 개별 DB 조회하지 않음 |
| Optional modules | 기존 SES의 Lifecycle, Archive, Reports, LearningSupport, Notifications, Scheduler와 연결 |

SES는 현재 구성 검증·PES 미리보기만 구현되어 있으며 운영 모듈은 준비되지 않았다.
선택된 구성이라는 이유만으로 메뉴나 실행 버튼을 활성화하지 않는다.
**설정 선택 + 실행 모듈 준비 + 서버 권한**을 모두 만족할 때만 제공한다.
초기 개선은 필수 수업·학생·과제·결과 UI에 집중하고, SES 웹 편집기는 후속 단계로 둔다.
개인별 교수자·조교 권한은 다교수자 운영과 민감한 지원 기록 기능의 선행 조건이다.

## 6. 실행 순서와 완료 기준

아래 우선순위는 이번 교수자 UX 작업 내 순서다. 전체 운영 보안·권한의 중요도를 낮추는 의미가 아니다.

| 단계 | 작업 묶음 | 완료 기준 |
| --- | --- | --- |
| 0 · 설계 확인 | 운영 홈, 과제 목록·상세, 6단계 작성, 학생 이력의 데스크톱/모바일 와이어프레임 | 교수자가 업무 흐름·대표 행동·용어를 확인한 뒤 구현 착수 |
| P0 · 오해·실수 방지 | 공개 상태 모순 수정, 과제 표 카드화, 마감/연장 제한 안내, 입력 오류 복구, 현재 점수/최고점 일관 표시 | 공개 여부·현재 제출·마감 오판이 없고 잘못 입력해도 처음부터 다시 작성하지 않음 |
| P1 · 일상 운영 | 단일 홈·수업 문맥, CLI/웹 과제 통합, 검색·페이지 나누기, 저장 경고, 케이스 편집, 검증 갱신 | 한 수업에서 등록→공개→학생 결과 확인을 CLI 없이 완료. 지원하지 않는 작업은 이유 명시 |
| P2 · 운영 확장 | 개인별 권한, 보고서, 안전한 초안 정리·과제 보관/복원 | 권한·데이터 보존·감사·복구 시험 완료 후 활성화. 단순 화면 변경으로 출시하지 않음 |
| P3 · 선택 기능 | SES 설정 화면, 설명 가능한 지원 후보·교수자 알림 | 준비된 모듈만 구성 가능, 근거·범위·비교 기준 확인 가능 |

단계별로 조회 모델/서비스 → 화면 → 회귀 시험 → 별도 시험 서버 확인 순서로 진행한다.
새 화면을 먼저 제한적으로 노출하고 기존 URL을 유지한다. DB 변경이 있으면 백업·복원과 구버전 호환을 별도로 확인한다.
이번 계획은 실행 인원과 운영 제약을 확인하기 전이므로 확정 일정이나 완료 날짜를 약속하지 않는다.

## 7. 검증 계획

### 기능·안전 시나리오

1. `come2201`, `come3105`, 같은 교과목의 2개 분반과 20명 이상 합성 학생으로 수업 전환·필터·집계 범위를 시험한다.
2. 웹·CLI 과제가 통합 표시되고 초안/릴리스가 중복 집계되지 않는지 확인한다.
3. C/C++ 예제와 직접 등록에서 파일 누락, 잘못된 ZIP, 배점 오류, 오답 예제 실패, 컴파일러 부재를 시험한다.
4. 저장 오류, 인증 만료, 다른 탭 수정, 검증 중 수정, 검증 후 변경이 입력 손실·무검증 공개로 이어지지 않는지 확인한다.
5. 예약 공개, 과거 마감, 마감 직전/정각/직후, 업로드 중 마감, 연장 충돌을 시험한다.
6. 같은 요청 재시도는 같은 접수본, 새 제출은 별도 접수본인지 확인한다. 대기 중 이전 점수가 최신으로 나타나지 않아야 한다.
7. 이력·diff가 다른 학생·분반 자료를 노출하지 않는지 직접 URL 접근도 확인한다.
8. CSV 오류·중복 등록·비활성화·이름 변경의 영향 범위와 개인정보 비노출을 확인한다.
9. 갱신 실패·네트워크 단절·큐 지연에서 마지막 기준 시각과 복구 방법이 표시되는지 확인한다.
10. 삭제·보관 구현 단계에서는 작업 중 충돌, 참조된 파일, 디스크 부족, 중단 후 재시작, 복원 무결성을 추가 시험한다.

### 화면·사용성 인수

- 320/375/768/1280/1440px, 밝은/어두운 테마, 긴 교과목명·학생명, 키보드만 사용한 경로를 확인한다.
- 일반 화면의 페이지 가로 넘침·버튼 겹침·읽을 수 없는 색상·잘린 오류 문구가 없어야 한다.
- 긴 코드 비교는 전용 영역에서 스크롤하며 원래 학생/과제 문맥을 잃지 않아야 한다.
- 주요 시험 과업: “올바른 분반에 과제 공개”, “마감 확인·연장”, “재제출 학생의 현재 점수·최고점·코드 차이 확인”.
- 교수자/조교 3~5명의 파일럿에서 도움 없이 과업 완료 여부·오선택·되돌아간 횟수를 기록한다.
  특히 다른 분반 변경, 공개 여부 오판, 이전 점수를 최신으로 오인한 사례는 출시 차단 항목으로 삼는다.
- 20명 이상 제출 중 교수자 현황 조회가 제출 접수와 SQLite 쓰기를 과도하게 지연시키지 않는지 기존 대비 측정한다.
  현재 계획에서는 미측정 응답 속도나 동시 접속 성능을 보장하지 않는다.

## 8. 후속 결정 사항

- 보고서의 최신/최고/교수자 확정 점수 선택 정책. 현황 UI와 최종 성적 정책은 분리한다.
- 학생별 유예·마감 단축·무기한 과제의 마감 추가 허용 여부와 학생 공지 절차.
- 과제·제출 소스의 보존 기간, 보관 금지·복원 권한, 영구 삭제 승인 절차.
- 개인별 교수자·조교·운영자 역할과 담당 수업 범위.

이 결정 전에도 단계 0과 P0의 화면 설계는 진행할 수 있다. 위험한 정책은 임의 기본값으로 활성화하지 않는다.

# Mac IDE 자동 업데이트

교수자가 승인한 Mac IDE를 자동으로 내려받고, 학생이 IDE를 종료한 뒤 **다음 실행에서** 사용한다.
실습 중에는 현재 버전을 유지한다. 학생의 코드·자료·로그인 정보는 기존 공용 실행기가 종료 시
삭제하며 업데이트 저장소에는 앱과 공개 승인 자료만 남는다. 학생이 명시적으로 내보낸 파일은
기존 정책대로 삭제하지 않는다.

교수자 승인은 이 버전에서 **기관 승인 파일에 서명하여 공개하는 운영 절차**로 제공한다.
기존 교수자 웹의 VSIX 배포 화면은 추가 확장용이며, 앱 전체 업데이트 승인 화면은 아니다.
학생이 Node.js를 설치하거나 터미널 명령을 실행할 필요는 없다.

## 동작 순서

1. 고정 채널 아이콘을 실행하면 이전 실행에서 받아 둔 업데이트를 확인한다.
2. 이전 실습의 실행·정리가 끝났고 새 버전의 서명·기관 승인·파일 검증이 통과하면 선택 버전을
   바꾸고 새 IDE를 실행한다. 다운로드만 완료했다고 실행 중인 IDE를 교체하지 않는다.
3. IDE가 실행되는 동안 설정된 HTTPS 피드에서 새 버전을 확인한다. 기본 운영 예시는 실행 시와
   이후 1시간 간격이다. 공개된 버전이 현재보다 새롭고 기관이 승인했으면 별도 폴더로 받는다.
4. 파일 검증을 마친 버전만 다음 실행 대기로 등록한다. IDE 종료 시 다운로드가 끝나지 않았다면
   그 다운로드를 중단하며, 다음 실행에서 다시 시도한다.
5. 원래 공용 실행기가 학생 작업 폴더와 로그인 프로필을 정리한다. 다음 클릭에 대기 버전이
   적용된다. 정리가 끝나지 않으면 업데이트를 강제로 적용하지 않는다.
6. 새 버전이 실행되지 않으면 이전 버전의 승인·파일과 실습 정리 상태를 확인하고 복귀한다.
   실패한 버전은 자동 재적용을 막는다. 고친 앱은 새로운 릴리스 ID와 더 큰 순번으로 공개한다.

학생 실습이 시작되기 전 실행 오류라면 확인된 이전 버전으로 바로 실행할 수 있다. 이미 실습을
시작한 뒤 앱이 비정상 종료된 경우에는 오류를 알리고 이전 버전을 다음 실행용으로 선택한다.
실습 중 오류를 숨기면서 새 학생 세션을 자동으로 만들지 않는다.

피드에 연결할 수 없거나 다운로드·검증에 실패하면 유효한 기존 설치본으로 실행한다.
**기존 버전까지 변조되었거나 기관 승인이 만료되었다면 실행을 허용하지 않는다.** 네트워크가
끊겼다는 이유로 서명·승인 검사를 생략하지 않는다.

## 1. 앱과 승인 자료 준비

[기관용 IDE 릴리스 검증·배치 적용](ide-signed-releases.md)의 1·2절에 따라 최종 Mac 앱을 만들고
릴리스 서명과 기관 승인을 준비한다. 앱 안에는 기관의 공개 API·포털 주소만 넣고, 학생 정보나
서명 개인키를 넣지 않는다. 다음 파일을 준비한다.

| 파일 | 내용 |
| --- | --- |
| `release-payload/Autograde IDE.app` | 완성된 Mac 앱 |
| `release.json` | 파일 목록·해시·진입점·호환 버전에 대한 배포자 서명 |
| `approval.json` | 특정 릴리스의 기관 승인·채널·유효기간에 대한 기관 서명 |
| `release-context.json` | 기관 공개키·허용 서버 버전·플랫폼·세션 경로·업데이트 주소 |

`sequence`는 같은 대상의 새 릴리스마다 증가시킨다. 배포 파일의 이름만 바꾸거나 같은 ID에
다른 앱을 덮어쓰지 않는다. 배포자 키와 기관 승인 키는 서로 다른 Ed25519 키를 사용한다.
개인키는 운영자의 별도 위치에 보관하고 서버의 공개 파일 폴더나 학생 PC에 복사하지 않는다.

`pilot`에서는 앱의 ad-hoc 서명을 사용할 수 있지만 제품 배포 승인을 의미하지 않는다.
`production`에서는 Developer ID 서명·Apple 공증·승인된 Apple Team ID 검증이 필요하다.
학교별 실제 인증서와 승인 키는 운영자가 설정한다.

## 2. Mac의 기관 설정

기존 `release-context.json`에 다음 항목을 추가한다. 주소는 일반 서버 자동 검색 결과와
분리된 운영자 설정이다. mDNS 응답으로 업데이트 주소나 신뢰 공개키를 바꾸지 않는다.

```json
{
  "extensionVersionPolicy": "institution-approved",
  "updates": {
    "feedUrl": "https://ai.cbchoi.info:20000/v1/ide-updates/pilot/darwin/arm64/feed.json",
    "checkIntervalSeconds": 3600
  }
}
```

위 내용은 **기존 설정에 합칠 항목**이며 전체 설정을 대체하지 않는다. 기존의 `institutionId`,
`channel`, `platform`, `architecture`, `serverRelease`, `extensionVersion`,
`institutionProfileSha256`, 공개키, `sessionRoots`를 유지한다. Intel Mac에는 `x64` 피드를 사용한다.

`extensionVersionPolicy`가 없으면 기존처럼 `extensionVersion`과 정확히 같은 확장만 허용한다.
`institution-approved`를 명시하면 새 내장 확장 버전도 앱 전체의 배포자 서명과 기관 승인을
통해 갱신할 수 있다. 서버 호환 버전·플랫폼·기관 프로필 검사는 그대로 유지한다.

기관 설정은 학생 작업 폴더 밖에 두고 다른 OS 사용자가 수정할 수 없게 한다. Mac 예시에서
`sessionRoots`에는 해당 좌석 OS 사용자의 `/private/tmp/ag-lab-UID`를 포함한다. `UID`는 장비의
실제 사용자 ID이며 문자열 `UID`를 그대로 넣지 않는다. 사용하는 공용 세션 경로를 모두 등록한다.
업데이트 저장소도 이 경로 밖에 둔다.

## 3. 서버에 공개

서버는 실행 CSV의 `data_root` 아래 `ide-updates`에서 읽기 전용으로 배포 파일을 제공한다.
별도 CSV 활성화 항목은 없으며 파일이 없으면 404를 반환한다. 다음처럼 플랫폼·CPU별 폴더를
분리하면 서로 다른 빌드를 같은 서버에서 운영할 수 있다.

```text
<data_root>/ide-updates/
  pilot/darwin/arm64/
    feed.json
    <SHA-256>.agupdate.gz
  pilot/darwin/x64/
    feed.json
    <SHA-256>.agupdate.gz
```

정식 채널은 `pilot` 대신 `production`을 사용한다. Mac에 설정한 채널과 승인 파일의 채널이
일치해야 한다. 피드는 기관 서명이 포함된 JSON이며, 승인 자료와 변경 불가능한 압축 파일을
가리킨다. 압축 파일에는 개인키·기관 운영 설정·학생 데이터를 포함하지 않는다.

공개할 디렉터리를 먼저 만든 뒤 다음 명령으로 배포 파일을 만든다. `--output`은 이미 존재하는
실제 디렉터리여야 한다. 여기서는 `/srv/autograde-data`가 서버 CSV의 실제 `data_root`라고
가정한다. 경로는 운영 환경에 맞게 바꾼다.

```sh
mkdir -p /srv/autograde-data/ide-updates/pilot/darwin/arm64
node ide/code-oss/update-transport.mjs publish \
  --payload release-payload --release release.json --approval approval.json \
  --context release-context.json --key /operator-keys/school.pem \
  --key-id school-2026 \
  --output /srv/autograde-data/ide-updates/pilot/darwin/arm64
```

배포 도구는 승인과 앱 파일을 재검증하고 압축 파일을 먼저 쓴 뒤, 완성된 `feed.json`을 원자적으로
교체한다. 개인키를 서버에 두지 않으려면 운영자 컴퓨터의 별도 공개용 디렉터리에서 이 명령을
실행한 뒤 생성된 두 공개 파일만 서버에 전송한다. 이 경우에도 압축 파일을 먼저 전송하고
마지막에 완성된 피드를 교체한다. 배포자의 앱 서명은 `release.json` 안에 유지된다. 기관은
자신의 승인 키로 피드를 서명하므로 배포자 개인키를 전달받거나 학생 장비에 넣을 필요가 없다.

`.agupdate.gz`는 `autograde-signed-files-gzip-v1` 형식이다. 서명된 파일 목록 순서에 따라
일반 파일 내용만 압축하고, 경로·권한·내부 링크는 서명된 목록에서 재구성한다. 임의의 ZIP이나
tar.gz를 이름만 바꾸어 사용할 수 없다. 클라이언트는 외부 경로 링크·경로 탈출·파일 크기 불일치를
거절한다. 피드는 최대 32 MiB, 압축 배포 파일은 최대 2 GiB다.

일반 `/v1/` API를 이미 같은 서버로 전달하는 Nginx 설정이면 새로운 전용 location은 필요하지
않다. 기존 학교 DNS·DHCP·hosts·방화벽 설정을 변경하지 않는다. HTTPS 인증서가 실제 도메인에
대해 유효해야 하며, 다운로드 경로에서 HTTP로 전환하거나 다른 도메인으로 리다이렉트하지 않는다.
업로드 요청이 아니라 GET 다운로드이므로 이 기능을 위해 `client_max_body_size`를 늘릴 필요는 없다.

파일 공개는 운영자가 만든 완성된 배포 디렉터리를 사용한다. 압축 파일을 먼저 배치하고 마지막에
`feed.json`을 원자적으로 교체한다. 복사 중인 파일을 피드에서 먼저 가리키지 않는다. 기존 압축
파일은 아직 다운로드 중인 좌석을 위해 보관한다. 서버에 비공개 서명 키를 올리지 않는다.

## 4. 최초 한 번 채널 아이콘 설치

처음에는 유효한 기존 버전 하나를 저장소에 넣고 활성화한다. 자동 다운로드가 실패해도 사용할
기존 버전이 필요하므로 빈 저장소만 배포하지 않는다. 아래 `/operator/...` 경로는 해당 Mac에서
운영할 실제 절대 경로로 바꾼다.

```sh
node ide/code-oss/release-channel.mjs stage \
  --store /operator/releases --payload release-payload \
  --release release.json --approval approval.json --context /operator/release-context.json
node ide/code-oss/release-channel.mjs activate \
  --store /operator/releases --id 최초-릴리스-ID --context /operator/release-context.json
node ide/code-oss/install-channel-launcher.mjs \
  --store /operator/releases --context /operator/release-context.json \
  --node .cache/node-v24.18.0-darwin-arm64/bin/node \
  --output 'dist/Autograde Channel.app'
```

생성한 채널 앱에는 Node와 자동 업데이트 코드가 포함된다. 이 준비는 운영자가 수행하며 학생은
배포된 아이콘만 실행한다. 기존 일반 Autograde IDE 아이콘은 이 채널을 자동으로 이용하지
않으므로 담당자가 최초 한 번 새 채널 아이콘으로 바꾸어 안내한다. 사용 중인 앱은 덮어쓰지 않는다.

앱과 저장소·기관 설정 경로는 장비에 맞아야 한다. 다른 Mac으로 아이콘만 복사하면 최초 버전이나
기관 설정이 누락될 수 있다. 각 장비에서 최초 저장소·설정·아이콘을 함께 준비한다. 업데이트 저장소는
0700, 기관 설정 파일은 0600으로 보호한다. 경로가 준비된 뒤 운영자는 다음처럼 확인·설정한다.

```sh
chmod 700 /operator/releases
chmod 600 /operator/release-context.json
```

동일한 OS 계정을 공유하는 학생에 대한
OS 수준의 격리는 이 경로 권한만으로 제공하지 않는다.

채널 아이콘 자체의 Node·서명 검증 코드 업데이트는 별도 채널 앱 교체가 필요하다.
현재 자동 업데이트 대상은 그 채널이 실행하는 IDE 앱이다. Windows·Linux 자동 업데이트 적용을
완료했다는 의미는 아니다.

앱 저장소는 학생 세션과 달리 종료 시 삭제하지 않는다. 현재 버전과 복귀용 이전 버전은 항상
유지한다. 새 앱을 받을 여유 공간이 없으면 업데이트를 적용하지 않고 기존 버전을 유지한다.
새 버전의 실제 실행과 종료 후 정리가 확인되면, 자동 다운로드한 오래된 버전을 정리한다.
현재 버전·복귀용 이전 버전·적용 대기 버전·실행 검증 중인 버전은 유지한다. 최초 설치본이나
운영자가 직접 stage한 버전은 자동 정리 대상이 아니므로 운영자가 보관량을 관리한다.
학생 자료 정리를 위해 앱 저장소 전체를 삭제해서는 안 된다.

## 문제 확인

| 증상 | 확인할 내용 |
| --- | --- |
| 새 버전을 받지 않음 | 해당 피드의 HTTPS 응답, 기관·채널·CPU, 더 큰 `sequence`, 기관 승인 유효기간 |
| 확장 버전 불일치 | 기관 설정의 명시적 `extensionVersionPolicy`와 새 앱의 기관 승인 |
| 다운로드 후 기존 앱이 실행됨 | 현재 실습이 종료되었는지, 다음 실행인지, 공용 폴더에 정리되지 않은 `current`나 잠금이 남았는지 |
| 실패한 버전이 재시도되지 않음 | 실패 버전 재적용 방지 동작이며, 수정본을 새 ID·더 큰 순번으로 재승인·공개 |
| 기존 앱도 실행되지 않음 | 기존 파일 변조·삭제, 승인 만료, 서버 호환 정책 변경, 세션 정리 실패 |
| 종료 후 자료가 남음 | 원래 공용 실행기의 정리 오류부터 해결; 업데이트 도구로 임의 삭제하거나 잠금을 무시하지 않음 |

저장소의 `update-state.json`에서 마지막 업데이트 상태와 대기·실패 릴리스를 확인할 수 있다.
이 파일에는 학생 코드·로그인 토큰을 기록하지 않는다. `ready-next-launch`는 검증 완료·다음 실행
대기, `kept-current`는 현재 버전 유지, `rolled-back`은 이전 버전 선택, `recovery-required`는
이전 실습 정리 또는 이전 버전 검증을 운영자가 확인해야 한다는 뜻이다.

비정상 종료 후 `.channel-lock.json`·`.launch-lock.json`이 남았으면, 다음 실행에서 파일 소유권과
권한을 검사하고 기록된 프로세스가 종료된 경우에만 실행 잠금을 복구한다. 살아 있거나 확인할 수
없는 프로세스의 잠금은 해제하지 않는다. 중단된 `.download-UUID` 폴더도 소유권·권한과 다운로드
프로세스의 종료를 확인한 경우에만 정리하며, 확인되지 않은 폴더는 삭제하지 않는다.

파일 배치·활성화 중단으로 **`.update-lock.json`**이 남은 경우에는 자동으로 해제하지 않는다.
운영자가 해당 프로세스의 종료와 앱 선택·공용 세션 정리 상태를 확인해야 한다. 실행 중인
프로세스가 있는 상태에서 잠금을 일괄 삭제하거나 학생 작업 폴더를 임의로 지우지 않는다.

서버의 피드·압축 파일은 공개 배포 자료다. 학생 비밀번호·세션 쿠키·토큰을 다운로드 인증에
사용하지 않는다. 앱 신뢰는 HTTPS 외에도 배포자 서명과 기관 승인으로 확인한다. 브라우저나
네트워크 관리자가 피드 JSON을 수정해도 유효한 두 서명을 대신할 수 없다.

## 검증과 실습실 인수

2026-10-30 Mac 로컬 검증에서는 IDE 관련 자동 시험 377개와 서버 관련 시험 60개가 통과했다.
다운로드 중 현재 버전 유지, 다음 실행 적용, 연결 실패·변조·실행 실패 시 이전 버전 유지 또는
복귀, 실패 버전 재적용 방지, 실제 공용 실행기의 코드·자료·로그인 파일 삭제를 확인했다.
시스템 PATH에 Node가 없는 조건에서 생성한 Cocoa 아이콘 실행 파일도 실행했다.

기존 Mac 앱 전체를 사용한 별도 검증 결과는 다음과 같다. 운영 서버나 실제 학생 계정은
사용하지 않았으며, 원본 앱을 변경하거나 전체 IDE GUI를 실행한 시험은 아니다.

| 검사 | 결과 |
| --- | --- |
| 앱 전체 목록 | 포장된 자료 71,538개, 내부 링크 15개 검증 |
| 압축 전 / 배포 파일 | 1,932,941,509 / 597,059,965 바이트 |
| 압축 복원 | 모든 파일 내용·실행 권한·내부 링크 일치 |
| Mac 앱 서명 | 원본·복원본·배치본의 `codesign --verify --deep --strict` 통과 |
| 배치 후 재검증·활성화 | 20,534,526바이트의 서명 메타데이터를 다시 읽고 다음 실행 준비 완료 |
| 시험 종료 | 시험용 큰 복사본 삭제, 원본 앱 유지 |

이 검증에서 기존 16 MiB 메타데이터 읽기 한계가 실제 Mac 앱에 부족함을 확인하여,
로컬 릴리스 메타데이터의 제한을 64 MiB로 늘렸다. 네트워크 피드 제한은 32 MiB를 유지한다.

자동 검증은 테스트용 Ed25519 키와 임시 배포 파일을 사용한다. 정상 업데이트, 위·변조 또는
승인 불일치 거절, 다운로드 실패 시 기존 버전 유지, 다음 실행 적용, 실패 버전 복귀와 공용
세션 정리 경계를 확인한다. 실제 학생 계정이나 운영 데이터로 시험하지 않는다.

개발 Mac에서 다음 명령으로 관련 검증을 실행한다. 네이티브 아이콘 빌드 시험에는 저장소가
지정한 Node 버전이 필요하므로 Mac 패키징에 사용하는 내장 Node를 사용한다. Intel 장비에서는
해당 x64 Node 경로로 바꾼다.

```sh
.cache/node-v24.18.0-darwin-arm64/bin/node --test \
  ide/code-oss/release-channel.test.mjs \
  ide/code-oss/channel-launcher.test.mjs \
  ide/code-oss/update-transport.test.mjs \
  ide/code-oss/auto-update.test.mjs \
  ide/code-oss/auto-update-https.test.mjs \
  ide/code-oss/mac-launcher.test.mjs \
  ide/code-oss/shared-session.test.mjs
.venv/bin/python -m pytest -q tests/unit/test_ide_update_distribution.py
```

HTTPS 검증은 테스트용 인증기관과 실제 로컬 HTTPS 서버로 다운로드를 수행한다. 채널 검증은
서명한 테스트 실행 파일과 공용 실행기 감독 코드를 사용해 코드·자료·로그인 파일의 정리를
확인한다. Mac 네이티브 아이콘 생성과 내장 Node 실행도 별도로 확인한다. 이 검증은 운영 기관의
Developer ID 공증이나 실제 학생 과제의 전체 GUI 인수를 대신하지 않는다.

실습실 배포 시에는 시험 좌석에서 A 버전을 실행한 채 B를 승인·공개하고, 수업 중 A 유지 →
종료 후 학생 파일·로그인 삭제 → 다음 실행 B 적용을 확인한다. 네트워크를 끊거나 잘못된
테스트 업데이트를 공개했을 때 유효한 A가 계속 실행되는지도 확인한다. 운영 승인 키로 서명한
실제 앱의 공증·학교 인증서·최종 GUI 시험은 해당 기관 환경에서 수행한다.

# 과제 제출·검증 단계별 UX 설계

작성: 2026-09-15. **UX·구현 계약 설계이며 아래 단계형 화면은 아직 구현되지 않았다.**
대상은 학생의 VS Code/Visual Studio 확장과 교수자의 과제 등록 웹이다.
[웹 과제 등록 MVP](instructor-assignment-web-mvp.md),
[수업·학생 등록 MVP](course-student-web-mvp.md)의 공통 인수 기준으로 사용한다.

## 1. 용어와 안내 원칙

- **제출 전 확인:** 학생의 저장 파일·대상 과제·업로드 가능 여부 확인. 정답 검사가 아니다.
- **서버 접수:** 서버가 제출을 받아 접수 ID와 시각을 확정한 상태. 채점 완료와 다르다.
- **자동 채점:** 접수된 코드의 컴파일·실행·평가. 점수 공개 정책에 따라 결과 표시가 늦을 수 있다.
- **교수자 채점 검증:** 공개 전 정답·오답을 채점해 과제 자료와 채점 설정을 점검하는 작업.
- 단계 제목, 현재 상태, 다음 행동을 항상 함께 표시한다. 설명을 읽지 않아도 주 버튼이 다음 행동을 알려준다.
- 단계 번호는 진행 순서이지 성공률이 아니다. 서버 근거 없는 퍼센트·예상 대기 시간·대기 순번을 표시하지 않는다.
- 서버 연결, 학생 로그인, 과제 수락, 제출 접수, 채점 결과를 서로 다른 상태로 표시한다.
- 공용 PC에서 안내의 “다시 시작”은 기존 파일·제출 기록 삭제를 의미하지 않는다.

## 2. 학생: 제출 전 진입 화면

확장의 현재 수락 과제 카드에서 **제출 준비**를 누르면 안내를 시작한다.
현재 수업/과제 제목, 마감(시간대 포함), 서버 주소, 선택한 폴더를 계속 표시한다.
학생 본인 확인용 학번은 화면에서만 보여 주고 토큰/비밀번호는 표시하지 않는다.
다른 과제는 현재 세션의 수락 범위를 벗어나므로 이 화면에서 선택하도록 하지 않는다.

| 시작 상태 | 안내 문구 | 주 행동 |
| --- | --- | --- |
| 서버 주소 없음 | “먼저 담당자가 안내한 서버 주소를 입력하세요.” | 서버 주소 설정 |
| 접속 불가 | “서버에 연결하지 못했습니다. 마지막 확인: {시각}.” | 연결 다시 확인 |
| 인증 없음/만료 | “웹에서 이 과제의 새 수령 코드를 발급받아 주세요.” | 수령 코드 입력 |
| 수락 과제 없음 | “아직 수락한 과제가 없습니다. 학생 웹에서 과제를 선택하세요.” | 학생 웹 열기 |
| 내려받은 폴더 없음 | “과제 파일을 내려받은 후 코드를 작성하세요.” | 과제 다운로드 |
| 수업/과제 접근 종료 | “현재 이 과제에 제출할 수 없습니다. 담당 교수자에게 확인하세요.” | 상태 다시 확인 |

학생 웹 주소는 서버가 제공한 검증된 공개 웹 origin을 사용한다. API 주소의 포트에 임의로
10을 더하지 않는다. 외부 링크의 origin 허용 규칙과 실제 서버 설정을 확인한다.
서버 시각의 마감 판정이 최종이며 PC 시계가 다르거나 업로드 중 마감될 수 있음을 안내한다.

## 3. 학생 제출: 5단계

| 단계 | 화면에 보여 줄 내용 | 주 버튼 / 보조 행동 | 다음 단계 조건 |
| --- | --- | --- | --- |
| 1. 파일 저장 | “저장된 파일만 제출됩니다.”, 폴더 경로, 필수 main.c/main.cpp | 저장 후 확인 / 폴더 열기 | 저장 확인, 과제-폴더 매핑 확인 |
| 2. 제출 파일 확인 | 포함 파일·제외 파일과 이유, 개수·용량, 제출 대상 과제 | 이 파일로 제출 / 이전 | 허용 형식·크기·경로 검사 통과 후 명시적 승인 |
| 3. 전송·접수 확인 | “전송 중”, 이후 서버가 확정한 접수 ID·시각 | 자동 진행, 필요 시 접수 확인 | 서버 접수 확인; 응답 불명은 별도 상태 |
| 4. 채점 상태 확인 | 접수됨/대기/채점 중, 최근 조회 시각 | 다시 확인 / 풀이 계속하기 | 서버 결과 공개 또는 종료 상태 확인 |
| 5. 결과·다음 행동 | 공개 점수·항목별 결과·수정 힌트, 선택 제출 ID·시각 | 수정 후 다시 제출 / 제출 기록 | 자동으로 재제출하지 않음 |

### 저장·파일 미리보기

- IDE 저장 API를 사용할 수 있으면 사용자의 “저장 후 확인” 동작으로 저장한다.
  지원되지 않는 환경은 “모두 저장 후 다시 확인”을 요청하고 실제로 저장했다고 표시하지 않는다.
- 해당 과제 폴더만 검사한다. 다른 과제·상위 workspace·현재 열린 다른 프로젝트를 제출하지 않는다.
- 제출 스냅샷을 만들고 그 스냅샷의 파일 목록을 미리 보여 준다. 승인 후 정확히 그 바이트를 보낸다.
  미리보기 이후 편집한 내용은 포함되지 않음을 표시하고 “파일 다시 확인”으로 새 스냅샷을 만든다.
- IDE별 제외 규칙을 그대로 보여 준다. VS의 .sln/.vcxproj/.exe 제외를 숨기지 않는다.
  제외된 파일의 이름과 이유만 보여 주고 이를 몰래 포함하지 않는다.
- 2단계 통과 문구는 “파일 형식 확인 완료 — 정답 여부는 서버에서 채점합니다.”로 한다.
  기존 실습 과제의 로컬 프로그램을 자동 컴파일·실행하지 않는다.

### 접수 완료와 채점 진행

- 접수 전에는 성공 체크나 “제출 완료”를 표시하지 않는다. 서버가 확정한 accepted receipt와
  submission_id가 확인되면 “서버 접수 완료”를 보여 준다. 단순 received 상태만으로 확정하지 않는다.
- 실제 서버가 queued/running까지만 제공하면 각각 대기/채점 중으로 표시한다.
  컴파일 중/실행 중/비교 중은 단계 이벤트를 서버가 제공하도록 추가한 뒤에만 사용한다.
- 데이터 전송량을 측정할 수 있을 때만 업로드 퍼센트를 표시한다. 아니면 불확정 진행 표시를 쓴다.
- 자동 결과 확인은 기본 5초 간격·최대 2분(기존 VS 흐름과 정렬), 이후 “자동 확인을 잠시
  멈췄습니다. 서버 채점은 계속될 수 있습니다.”와 수동 확인 버튼을 제공한다.
  429의 Retry-After를 존중하고 통신 실패에는 제한된 backoff를 적용한다.
- 접수 후 안내 창을 닫는 것은 제출 취소가 아니다. “풀이 계속하기”는 채점을 취소하지 않는다.
  전송 취소도 서버 접수를 철회한다고 보장하지 않는다. 서버 취소 API 없는 취소 버튼은 제공하지 않는다.

### 결과 표시

- 성공은 “채점 완료”, 만점/부분 점수는 숫자로 구분한다. 컴파일 실패처럼 0점인 정상 평가도
  전송 실패나 서버 장애와 구분한다. 점수만 보고 합격/불합격 기준을 추정하지 않는다.
- 공개된 컴파일 진단은 안전한 상대 파일 경로·줄 번호 링크로 연결한다.
- 비공개 케이스 입력·정답·교수자 코드·내부 절대 경로는 공개하지 않는다.
- 결과 공개 대기는 “접수 확인됨 · 결과 공개 대기”로 안내한다. API가 채점 완료를 확정하지
  않으면 “채점 완료”라고 덧붙이지 않는다. 공개 시각은 서버가 제공한 경우에만 표시한다.
- “최신 제출 결과”와 “현재 선택한 제출 결과”를 구분한다. 새 제출 채점 중에 이전 점수를
  새 결과처럼 보여 주지 않는다. 동일 내용 재제출이 합쳐지면 “동일한 접수 기록을 확인했습니다.”로 표시한다.
- 제출 기록은 서버 ID/접수 시각/해시로 식별하고 클라이언트 임의의 v1/v2를 공식 버전으로 쓰지 않는다.
  이전 코드는 새 폴더로만 복원하며 복원 자체는 제출·실행이 아니다.

## 4. 학생 오류·복구 안내

| 상황 | 화면 문구 예시 | 복구 동작 |
| --- | --- | --- |
| 미저장/필수 파일 없음 | “main.c가 없거나 저장 여부를 확인하지 못했습니다.” | 폴더·파일 확인 단계로 복귀 |
| 링크·금지 파일·용량 초과 | “이 파일은 제출할 수 없습니다: {안전한 상대 경로}, {사유}.” | 파일 수정 → 스냅샷 다시 만들기 |
| 전송 전 연결 끊김 | “아직 제출을 보내지 못했습니다.” | 연결 확인 후 제출 준비 재개 |
| 전송 후 응답 유실 | “접수 여부를 확인하지 못했습니다. 먼저 제출 기록을 확인합니다.” | 기록 조회; 같은 세션·스냅샷 재시도에는 동일 idempotency key |
| 서버 429 | “요청이 많아 잠시 기다려야 합니다.” | Retry-After 이후 재확인, 연속 클릭 방지 |
| 인증 만료 | “로그인이 만료되었습니다. 작성 파일은 그대로 남아 있습니다.” | 새 수령 코드 → 같은 과제 접수 기록 조회 |
| 마감 거절 | “서버 기준 제출 시간이 지났습니다. 이번 제출은 접수되지 않았습니다.” | 교수자 문의, 이전 접수 기록은 별도 확인 |
| 채점 환경 장애 | “제출은 접수됐지만 채점을 완료하지 못했습니다.” | 접수 ID와 문의 정보 제공; 학생 0점으로 확정 금지 |
| 결과 미공개 | “결과 공개를 기다리고 있습니다. 다시 제출할 필요는 없습니다.” | 결과 다시 확인 |
| 서버/API 버전 불일치 | “이 기능을 사용하려면 서버 또는 확장 업데이트가 필요합니다.” | 필요한 구성요소 안내, 접근 범위 우회 금지 |

접수 여부 불명의 경우 로컬 파일을 자동 삭제하지 않는다. IDE 재시작 후에는 메모리 토큰·재시도
키가 없어지므로 새 코드 인증과 서버 기록으로 확인한다. 전체 제출 스냅샷/자격 증명을 새로
디스크에 저장하는 기능을 이번 UX에 몰래 추가하지 않는다. 실제 미접수 또는 기존 중복 처리
규칙을 확인한 후에만 사용자가 재전송한다. 기록에 없다는 사실만으로 서버 미접수를 확정하지 않는다.

마감 후 새 코드 발급이나 숨긴 과제의 기록 조회가 현재 제한될 수 있다. 이 경우 “다시 로그인하면
항상 복구됩니다”라고 안내하지 않고, 접수 ID가 있으면 이를 사용해 교수자 확인을 요청한다.
문의 정보 복사는 오류 분류·과제 제목·접수 ID·발생 시각만 포함하며 토큰·비밀번호·소스는 제외한다.

## 5. 교수자: 공개 전 검증의 내부 체크리스트

교수자 화면은 별도 [과제 자료 제출·검증 UX](instructor-assignment-validation-ux.md)의
통합 작성 화면이 기준이다. 아래 4개 항목은 같은 화면 안의 내부 확인 체크리스트이며 별도 상위 마법사로 표시하지 않는다.

| 단계 | 확인 항목 | 주 행동 | 완료 기준 |
| --- | --- | --- | --- |
| 1. 자료 점검 | 언어·학생 파일·문제 설명·테스트 배점·정답/오답 역할 | 자료 확인 | 필수 자료와 안전 검사, 만점·오답 기대 점수 유효 |
| 2. 검증 실행 | 고정된 초안 revision, 사용할 정답/오답, 실행 제한 | 검증 시작 | 작업 ID 발급, 비동기 queued/running 표시 |
| 3. 검증 결과 | 정답 기대/실제 점수, 오답 기대/실제 점수, 오류 분류 | 공개 내용 확인 또는 설정 수정 | 최신 revision의 모든 필수 검증 통과 |
| 4. 공개 확인 | 교과목·학기·분반·기간·학생용 다운로드 목록·점수 공개 정책 | 과제 공개 | 원자적 공개 성공 응답과 학생 링크 |

정답만 맞으면 통과하지 않는다. 예를 들어 Hello World의 정답 10/10, 미완성 코드 5/10을
모두 만족해야 한다. 직접 만든 과제는 교수자가 지정한 오답 기대 점수를 사용한다.
검증 결과는 교수자 전용이며 학생 제출·성적 통계에 포함하지 않는다.

### 실패 시 다음 행동

- 정답 점수 부족: “정답 예제가 만점을 받지 못했습니다.” → 실패 케이스·비교 규칙·정답 파일 확인.
- 오답 기대 불일치: “오답 예제의 실제 점수가 설정과 다릅니다.” → 기대 점수/오답/배점 확인.
- 도구 부재: “서버 컴파일러를 사용할 수 없습니다.” → 운영자 확인. 학생 자료 수정으로 유도하지 않음.
- 비밀 자료 혼입: “학생 다운로드에 교수자 전용 자료가 포함될 수 있습니다.” → 자료 분리 단계.
- 검증 중단: “서버 재시작 등으로 검증이 중단되었습니다.” → 정리 완료 확인 후 재검증.
- 검증 후 자료 수정: “자료가 변경되어 다시 검증해야 합니다.” → 공개 비활성, 새 revision 검증.
- 공개 응답 유실: 공개 상태 조회를 먼저 수행. 새 과제나 새 버전을 자동 생성하지 않음.

오류 메시지는 해당 단계에 남기고 정상 입력을 유지한다. 단, 재인증이 필요하면 비공개 자료가
로컬 캐시에 남지 않도록 한다. 서버에 저장된 초안은 권한 확인 후 복구한다.
검증 성공 문구는 “등록한 정답·오답 예제의 검증을 통과했습니다.”이며 모든 입력의 정확성이나
보안 격리·일반 학생 배포 승인을 의미하는 “완전히 안전함” 문구는 사용하지 않는다.

## 6. 화면·MVC·통신 계약

- 두 확장과 웹에 단계 표시, 확인 목록, 상태 배지, 오류 패널, 접수 영수증, 결과 카드의
  명칭·순서를 공통 적용한다. 실제 구현은 VS Code UI와 Visual Studio WPF에 각각 맞춘다.
- 글꼴/색상/간격은 수업·학생 설계의 공통 토큰을 따른다. 키보드 이동, 포커스, 스크린리더 상태
  알림, 200% 확대에서 긴 파일 경로·오류 메시지 표시를 검증한다. 상태 갱신이 입력 포커스를 빼앗지 않는다.
- 1개 주 버튼과 보조 행동을 사용한다. 비활성 버튼에는 이유를 표시하며 툴팁에만 숨기지 않는다.
- Model/Service가 접수·revision·권한·공개 여부를 결정하고 Controller/Presenter가 이를
  학생/교수자용 ViewModel로 변환한다. View가 시간 경과나 로컬 클릭으로 성공 상태를 만들지 않는다.
- 학생 ViewModel: 과제/수업, 단계, 접수 여부(미접수/확인됨/불명), submission_id,
  received_at, 공개 가능한 결과, 마지막 조회 시각, 허용 행동, 안전한 오류 코드.
- 교수자 ViewModel: draft revision, validation job/check ID, 검증 사례 결과,
  publishable 및 불가 사유, public availability. 결과는 해당 revision에만 연결한다.
- API가 제공하지 않는 상세 진행률·세부 단계는 추가 서버 이벤트 계약 전까지 표시하지 않는다.
  기존 API로 알 수 있는 상태를 우선 재사용하고 새 필드는 선택적으로 추가한다.
- 오래된 요청의 늦은 응답이 학생 로그아웃·과제 전환 후 화면을 덮어쓰지 못하게 세션/과제/
  submission_id/revision을 확인한다. 전환 시 진행 안내를 분리하고 중복 제출 버튼을 잠근다.
- 현재 구현의 원시 state 문자열 표시, VS의 연속 확인창, VS Code 명령 중심 동작은 이 계획에
  따라 단계 패널로 개선할 대상이다. 새 버튼·자동 저장·파일 제외 상세·복구 자동화는 아직 미구현이다.

## 7. 구현 순서와 사용성 시험

1. 상태·문구·오류 분류의 공통 계약을 확정하고 단위 시험을 만든다.
2. 학생 1~3단계(저장·스냅샷 확인·접수 확인)를 구현한다.
3. 학생 4~5단계와 재접속·응답 유실·기록 복구를 연결한다.
4. 교수자 웹 마법사에 검증 4단계와 공개 제한을 적용한다.
5. 실제 HTTPS + VS Code + Visual Studio Community에서 수동 UX 시험을 수행한다.

합성 계정과 사전 검토 코드로 학생 역할 5명·교수자 역할 2명의 초기 사용성 시험을 제안한다.
참여자·성과는 아직 확보하지 않았으며 다음은 목표다.

- 설치/서버 장애를 제외하고 별도 구두 설명 없이 학생 5명 중 4명 이상이 첫 제출 완료.
- 모든 참여자가 접수 완료와 채점 완료, 채점 환경 장애와 학생 오답을 구분.
- 교수자 2명 모두 정답/오답 검증 실패 원인을 찾아 수정·재검증·공개 완료.
- 잘못된 과제/폴더 제출, 비공개 자료 유출, 응답 유실로 인한 불필요한 중복 접수 0건.
- 미저장·포함/제외 파일·마감 경계·코드 만료·중복 클릭·통신 중단·결과 미공개·서버 재시작을 시험.
- 이전 점수의 새 제출 오표시, 다른 학생/과제 응답 혼입, 로그아웃 후 자격 정보 잔류 0건.
- 25명 동시 시험에서도 단계 상태가 서버 기록과 일치하고, 큐 대기를 접속 실패로 표시하지 않음.

완료 시간·멈춘 단계·오클릭·도움 요청·복구 성공 여부를 기록하되 비밀번호/코드/학생 소스는
수집하지 않는다. UX 문서와 실제 화면이 일치하는지 확인한 뒤에만 단계 안내 완료로 보고한다.

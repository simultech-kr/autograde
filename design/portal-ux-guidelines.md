# Autograde 공통 UX 설계·개발 지침

문서 버전: 1.0 · 갱신: 2026-11-19 · 적용: 신규 기능과 변경하는 기존 기능

이 문서는 교수자·학생·기관 관리자 포털, Code-OSS IDE, VS Code·Visual Studio 확장,
실습실 실행기와 이후 추가할 모듈의 공통 설계 기준이다. 다른 교육용 제품에 재사용할 때도
공통 원칙을 유지하고 역할·용어·업무 흐름을 해당 제품에 맞게 정의한다.

**설계 요구사항과 구현 완료는 다르다.** 이 문서에 규칙이 있다는 이유로 현재 제품이 모두 지원하거나
접근성 인증을 받았다고 표시하지 않는다. 구현·시험·배포 상태는 기능별 검토 기록으로 확인한다.
기존 파일명은 문서 링크의 연속성을 위해 유지한다.

## 1. 문서 사용법과 규칙의 강도

새 화면이나 작업 흐름을 설계할 때 [UX 설계·검토 양식](templates/ux-design-review.md)을 복사한다.
사용자 작업, 진입·복귀 경로, 화면 상태, 인수 시나리오를 먼저 작성한 뒤 구현한다.
작은 수정은 관련 항목만 작성하며, 적용하지 않는 항목에는 이유를 남긴다.

| 표현 | 적용 방법 |
| --- | --- |
| **필수** | 출시 전에 만족해야 하는 기준. 미충족이면 결함 또는 명시적인 예외로 관리 |
| **권장** | 기본 선택. 다른 선택을 하면 사용자·환경 근거를 기록 |
| **선택** | 해당 기능·기기·제품 구성에서 필요할 때 적용 |
| **예시** | 설명을 위한 시나리오·문구이며 서버의 실제 정책이나 구현값이 아님 |

규칙 ID는 검토·이슈·PR에서 참조한다. 예: `FORM-03 저장 결과 불확실 상태 처리`.
규칙을 삭제할 때 ID를 재사용하지 않고 변경 이력에 대체 규칙을 적는다.

| 문서 | 역할 |
| --- | --- |
| 이 문서 | 공통 사용자 경험과 검증 기준 |
| [포털 IA Map](../docs/architecture/portal-information-architecture.md) | 메뉴·경로·상위 화면의 기준 |
| 기능별 설계·API 계약 | 권한, 상태 전이, 정책, 데이터의 의미 |
| [운영 문서](../docs/README.md) | 실제 설정·배포·복구 방법과 지원 범위 |
| 기능별 검토·시험 기록 | 시험한 버전·환경·결과·미확인 항목 |

문서가 서로 다르면 실제 정책과 사용자 요구를 확인해 관련 문서·화면·시험을 함께 맞춘다.
디자인 변경만으로 성적·인증·보관 정책을 바꾸지 않는다. 시안이나 목표를 완료 증거로 사용하지 않는다.

## 2. 근거와 제품 원칙

Google Material과 Apple Human Interface Guidelines는 우선순위·일관성·적응형 배치의 참고 근거다.
특정 플랫폼의 모양을 그대로 복제하거나 특정 프레임워크 도입을 요구하지 않는다.
웹 접근성의 목표는 WCAG 2.2 AA이며, 아래 선별 검사만으로 전체 준수를 선언하지 않는다.

| 근거 | 제품에서 사용하는 원칙 |
| --- | --- |
| [Google Material 버튼](https://developer.android.com/develop/ui/compose/components/button) | 주요 작업·보조 작업의 시각적 우선순위 |
| [Apple HIG 레이아웃](https://developer.apple.com/design/human-interface-guidelines/layout) | 창 크기가 바뀌어도 관계와 기능을 유지하는 배치 |
| [WCAG 2.2](https://www.w3.org/TR/WCAG22/) | 지각·조작·이해·호환성에 관한 검증 가능한 기준 |
| [WAI-ARIA 모달 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) | 대화상자의 이름, 키보드 이동, 열기·닫기 후 초점 |
| [Google Web Vitals](https://web.dev/articles/vitals) | 로딩·상호작용·레이아웃 안정성의 측정 |

다음은 위 근거를 제품에 적용한 **우리의 설계 결정**이다.

| ID | 필수 원칙 | 설계에서 답할 질문 |
| --- | --- | --- |
| UX-01 | 사용자 작업 중심 | 이 화면에서 사용자가 끝낼 일은 무엇인가? |
| UX-02 | 역할·수업·대상 구분 | 누구의 어느 수업·과제·파일을 다루는가? |
| UX-03 | 확인된 상태 표시 | 서버 확인인가, 로컬 상태인가, 추정인가? |
| UX-04 | 실수 예방과 복구 | 잘못 누르거나 연결이 끊겨도 어디서 이어가는가? |
| UX-05 | 필요한 상세의 단계적 제공 | 지금 판단할 정보와 나중에 볼 정보는 무엇인가? |
| UX-06 | 같은 의미에 같은 이름·동작 | 웹과 IDE에서 같은 작업을 다르게 설명하지 않는가? |
| UX-07 | 접근성과 개인정보 보호 | 별도 도움 없이 조작하고 다른 사용자의 자료 노출을 막을 수 있는가? |

링크를 모두 없애는 것이 목표가 아니다. 탐색은 링크, 실행은 버튼을 사용하고 중요한 작업을
발견하기 쉽게 배치한다. 클릭 수를 줄이기 위해 공개 확인이나 복구 수단을 없애지 않는다.

## 3. 사용자 역할과 핵심 작업

| 역할 | 우선 작업 | 기본 화면에 필요한 정보 | 경계 |
| --- | --- | --- | --- |
| 학생 | 수업 선택, 수령·실습·제출, 피드백 확인 | 현재 수업·과제, 다음 행동, 마감, 최신 제출 | 본인의 허용된 자료·공개 결과 |
| 교수자 | 과제 작성·검증·공개, 학생 지원, 결과 검토 | 현재 분반, 확인할 학생·작업, 공개 상태 | 담당 수업과 학생에게 보이는 범위 |
| 기관 관리자 | 계정·수업·실습실·서버 운영 | 운영 이상, 영향 범위, 복구 방법 | 기관 전체와 특정 수업 작업 |
| 공용 PC 이용자 | 인증, 복원, 실습, 내보내기, 종료 | 현재 사용자, 서버 저장 시각, 정리 정책 | 이전 사용자 파일·세션·화면 노출 방지 |

**ROLE-01 필수:** 역할 전환이나 메뉴 숨김은 권한 검사를 대신하지 않는다.
조회·변경·다운로드마다 서버가 권한을 확인하고, 화면은 허용된 작업만 안내한다.

**ROLE-02 필수:** 역할이 여러 개인 사람도 현재 역할을 알아야 한다. 학생 미리보기는 실제 학생
세션과 구별한다. 관리자 전체 범위 작업에는 영향 수업·대상 수를 표시한다.

**ROLE-03 권장:** 처음 필요한 설정을 순서대로 안내하되 반복 사용자에게 전체 안내를 강제하지 않는다.
도움말에서 다시 볼 수 있게 한다.

## 4. Information Architecture와 탐색

**IA-01 필수 — 화면 주소:** 모든 업무 화면에 역할, 상위 화면, 메뉴 그룹, 제목,
직접 진입 조건, 오류 시 복귀 경로를 정의한다. 새 기능은 IA Map에 등록한 뒤 메뉴에 연결한다.

**IA-02 필수 — 공통 틀:** 같은 역할의 화면은 같은 메뉴 순서·이름·현재 메뉴 표시를 사용한다.
수업 문맥에서는 교과목명·분반을 유지한다. 사용자에게 익숙한 이름을 우선하고 내부 키는 상세에 둔다.
동명 과제는 주차·분반·생성 순서 등 의미 있는 보조 정보로 구별한다.

**IA-03 필수 — 돌아가기:** 직접 주소로 접속해도 동작하는 상위 링크를 제공한다.
목록에서 들어온 상세는 허용 목록으로 검증한 검색·필터·정렬·페이지를 유지해 돌아간다.
유효한 문맥이 없으면 해당 수업의 기본 목록으로 복귀한다. 임의 외부 URL이나 `history.back()`에만 의존하지 않는다.

**IA-04 필수 — 문맥 경계:** 수업이나 사용자를 바꾸면 이전 수업 전용 필터·선택 대상을 초기화한다.
로그인·권한이 바뀌면 이전 사용자 데이터를 표시한 채 새 요청을 진행하지 않는다.

**IA-05 권장 — 기본 배치:** 공통 탐색·수업 문맥 → 돌아가기·현재 위치·제목 → 핵심 작업/상태 →
검색·주 콘텐츠 → 상세 설정·이력·도움말 순으로 구성한다. 같은 대상을 보는 관점 전환에는 탭을 사용한다.
팝업은 짧은 확인·상세에, 긴 작성·비교·여러 단계 작업은 전용 페이지에 둔다.

**IA-06 필수 — 공개 경로:** 메뉴·복귀·다운로드에는 배포된 공개 기본 주소와 허용된 경로를 사용한다.
내부 전용 호스트·관리 포트를 노출하거나 개발 미리보기와 운영 링크를 섞지 않는다.

## 5. 시각 체계와 반응형 배치

**VIS-01 필수:** 공통 의미 토큰을 사용한다. 색상·글꼴·간격·테두리·초점을 화면마다 새로 정하지 않는다.
현재 평면 디자인을 유지하며 구획은 여백·배경·선으로 구별한다. 테마별 색을 하드코딩하지 않는다.

| 항목 | 제품 기본값 | 적용 방법 |
| --- | --- | --- |
| 간격 | 4px 단위, 주로 8·16·24px | 서로 다른 작업 사이 간격을 관련 항목 안쪽보다 크게 |
| 본문 | 16px 상당, 줄 높이 약 1.5–1.6 | 상대 단위·글자 확대 지원; 고정 높이로 자르지 않음 |
| 메뉴·표 | 14px 상당 이상 | 중요한 학번·점수·마감을 보조 글자 크기로 축소하지 않음 |
| 제목 | 24–28px 상당 | 최상위 제목을 명확히 하고 제목 단계 유지 |
| 주요 조작 영역 | 최소 44×44 CSS px, 터치 우선 48×48 권장 | 아이콘 그림이 아닌 실제 클릭 영역 기준 |
| 표·코드 | 내용에 맞는 폭 | 숫자 정렬, 코드 줄바꿈·부분 스크롤 선택 제공 |

이 치수는 **제품 기준**이다. Android dp, Apple pt, CSS px를 동일 단위로 취급하지 않는다.
WCAG 2.2 AA의 포인터 대상 기준은 예외를 포함한 24×24 CSS px 또는 간격 조건이며,
우리의 44/48 목표를 WCAG AA 원문 요구로 설명하지 않는다.
[대상 크기 기준](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

**VIS-02 필수:** 밝은·어두운 테마에서 본문 대비 4.5:1, 조작부·상태를 식별하는 비텍스트 대비 3:1을
검사한다. 큰 글자의 규정상 예외가 있어도 기본 텍스트 토큰은 4.5:1을 목표로 한다.
색만으로 상태를 구별하지 않고 선택 표시·아이콘·문구를 함께 제공한다.
[텍스트 대비](https://www.w3.org/TR/WCAG22/#contrast-minimum) · [비텍스트 대비](https://www.w3.org/TR/WCAG22/#non-text-contrast)

**VIS-03 필수:** 화면 폭을 줄여도 정보·행동의 의미를 유지한다. 320 CSS px 상당에서 일반 콘텐츠가
양방향 스크롤을 요구하지 않게 한다. 코드·복잡한 표처럼 2차원 배치가 필요한 부분은 라벨이 있는
부분 스크롤과 키보드 접근을 제공하고 페이지 전체의 가로 넘침을 방지한다.
[Reflow 기준](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

**VIS-04 권장:** 표를 카드로 바꿀 때 필드명·정렬·선택·데이터를 보존한다. 중복 DOM 때문에
보조기기에 두 번 읽히지 않게 한다. 고정 작업 막대가 초점·오류·마지막 행을 가리지 않도록 한다.

**VIS-05 필수:** 긴 한국어 제목, 공백 없는 파일명, 다자리 점수, 이름 없는 학생을 시험한다.
말줄임으로 숨긴 정보는 키보드·터치로 확인할 수 있어야 한다. 설명을 툴팁에만 넣지 않는다.

**A11Y-01 필수 — 조작:** 핵심 작업을 키보드로 완료할 수 있게 한다. 클릭 가능한 일반 요소보다
버튼·링크 등 의미가 있는 기본 요소를 사용하고, 포인터·드래그에만 의존하는 작업에는 대체 조작을 제공한다.
기본 초점 표시를 제거하지 않으며, 초점이 고정 헤더나 팝업 뒤에 가려지지 않게 한다.

**A11Y-02 필수 — 의미:** 문서 제목·언어·제목 계층·본문 영역을 정의하고 반복 탐색을 건너뛸 경로를 제공한다.
컨트롤의 이름·역할·선택/펼침 상태, 표의 헤더 관계를 보조기기에 전달한다.
네이티브 IDE 화면도 플랫폼 접근성 API에서 같은 의미를 제공해야 한다.

**A11Y-03 필수 — 확대와 동작:** 글자 확대 시 내용·기능을 잃지 않게 한다.
움직임 감소 설정을 존중하고, 애니메이션을 없애도 진행 상태를 이해할 수 있게 한다.
자동 이동·깜빡임·카운트다운으로 작업을 방해하지 않는다. 애니메이션은 완료의 유일한 증거가 아니다.

이 접근성 규칙은 WCAG의 키보드·초점·의미·확대 기준을 제품에 적용한 것이다.
움직임 감소 등 제품이 추가한 요구를 모두 AA의 원문 요구라고 설명하지 않는다.
검토 양식에 자동 검사뿐 아니라 키보드·실제 화면 읽기 도구의 시험 결과를 남긴다.
[WCAG 2.2 기준](https://www.w3.org/TR/WCAG22/)

## 6. 공통 컴포넌트와 상호작용 계약

| ID | 필수 규칙 | 예시 |
| --- | --- | --- |
| CMP-01 | 이동은 링크, 실행은 버튼; 목적이 드러나는 이름 | `새 과제 등록`, `성적 공개 검토`, `자료 ZIP 받기` |
| CMP-02 | 한 작업 영역의 최종 행동을 우선 강조; 보조·위험 작업 구분 | 저장은 채운 버튼, 취소는 보조, 삭제는 별도 영역 |
| CMP-03 | 아이콘 단독 조작에는 접근 가능한 이름과 충분한 영역 | 닫기·복사; 중요 제출 작업은 글자도 표시 |
| CMP-04 | 입력 이름·필수 여부·형식·제약을 입력 전에 표시 | placeholder를 label 대용으로 사용하지 않음 |
| CMP-05 | 비활성 이유와 다음 행동을 근처에서 확인 가능 | `검증 성공 후 공개할 수 있습니다` |
| CMP-06 | 빈 상태를 원인별로 구분 | 아직 없음 / 검색 결과 없음 / 권한 없음 / 연결 실패 |
| CMP-07 | 접힌 영역에 오류가 있으면 열고 오류로 이동 | 잘못된 기간 입력 후 펼쳐진 수정 폼 |
| CMP-08 | 표준 의미 구조·기본 컨트롤 우선 | 사용자 정의 조작은 키보드·보조기기 검증 필요 |

**CMP-09 필수 — 대화상자:** 이름·닫기 수단을 제공하고 모달에서는 배경 조작을 막는다.
내부로 초점을 이동시키고 Tab·Shift+Tab을 처리하며 Escape로 취소·닫을 수 있게 한다.
닫으면 원래 버튼 또는 자연스러운 작업 위치로 초점을 돌린다. 화면을 닫는다고 서버 작업을 취소하지 않는다.
비가역 작업의 기본 초점은 안전한 선택에 둔다. 복잡한 팝업 중첩을 피한다.
[WAI-ARIA 대화상자](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

**CMP-10 필수 — 검색:** 적용 조건·결과 수·전체 범위와 조건 해제 수단을 제공한다.
검색·정렬 변경 시 첫 페이지로 이동한다. 전체 집계와 필터 집계를 구분한다.
URL 조건도 로그·주소 공유로 학번 등이 노출될 수 있으므로 최소화하고 로그에서 보호한다.
비밀번호·토큰·수령 코드는 주소나 분석 이벤트에 넣지 않는다.

**CMP-11 필수 — 일괄 작업:** 선택 수와 `현재 페이지`/`검색된 전체` 범위를 명시한다.
필터 변경 후 숨겨진 대상을 조용히 유지하지 않는다. 대상 변경 시 재검토하고 부분 실패는 성공·실패 대상을 구분한다.
대상이 없으면 작업을 접거나 비활성화한다. 선택 해제 후 초점은 남아 있는 조작으로 이동한다.

**CMP-12 권장 — 알림:** 일상 완료는 본문 상태나 짧은 알림으로, 지속 장애는 작업 근처에 둔다.
오류·공개 영향·복구 버튼을 자동으로 사라지는 알림에만 넣지 않는다. 중복 알림·불필요한 모달을 줄인다.

## 7. 입력·저장·오류·비동기 처리

**FORM-01 필수 — 입력 유지:** 검증 실패 시 같은 사용자·인증 범위의 입력과 검색 문맥을 유지한다.
필드 오류와 상단 요약을 연결하고 수정 위치로 이동할 수 있게 한다. 파일 선택은 브라우저 보안상 재설정할 수
없으므로 유지 가능한 현재 탭의 참조와 재선택 필요를 구분한다.

**FORM-02 필수 — 저장 표시:** `편집 중`, `저장 중`, `서버 저장 확인`, `저장 확인 필요`를 구분한다.
미저장 변경이 있을 때만 이탈 경고를 제공한다. 서버 확인 버전·시각을 근거로 완료를 표시한다.
민감한 초안을 브라우저 영구 저장소에 임의 보존하지 않는다.

**FORM-03 필수 — 불확실:** 응답 유실·타임아웃은 변경 실패의 증거가 아니다.
접수·저장 상태를 먼저 조회하고 안전한 재시도가 지원될 때 같은 작업 식별자로 재시도한다.
새 공식 제출이나 공개 작업을 중복 생성하지 않는다.

**FORM-04 필수 — 동시 편집:** 다른 탭·교수자의 변경을 조용히 덮어쓰지 않는다.
입력을 유지하면서 최신본과 비교·재적용할 수 있게 한다. 서버 버전 검사를 UI만으로 대체하지 않는다.

**FORM-05 필수 — 인증 경계:** 세션 만료·로그아웃·사용자 교체·권한 회수 후 민감한 화면을 지운다.
복구를 위해 인증을 우회하지 않는다. 같은 사용자가 재인증한 뒤에만 허용된 서버 초안을 복원한다.

모든 비동기 작업은 다음 상태를 설계하고 실제 API 상태와 대응표를 만든다.

| ID·상태 | 사용자에게 보일 내용 | 다음 행동 |
| --- | --- | --- |
| STATE-01 초기·로딩 | 확인 중인 작업; 아직 결과가 없음 | 기다리기·조회 취소; 이전 결과는 이전 것임을 표시 |
| STATE-02 준비·빈 결과 | 결과 또는 비어 있는 이유 | 다음 작업·조건 초기화·권한 확인 |
| STATE-03 처리 중 | 실제 확인된 단계; 알 때만 백분율 | 중복 실행 방지·허용된 취소 |
| STATE-04 성공 | 어떤 대상에 어떤 변경이 확인됐는지 | 결과 보기·다음 작업 |
| STATE-05 오류 | 실패 단계·영향·복구 행동 | 수정·상태 조회·재시도·진단 확인 |
| STATE-06 부분 성공 | 완료·미완료 대상, 기존 데이터 상태 | 미완료 대상만 검토·재시도 |
| STATE-07 불확실·오래됨 | 마지막 서버 확인 시각, 확정할 수 없는 내용 | 다시 확인; 실패·0점 추정 금지 |
| STATE-08 인증·권한 | 재인증 필요 또는 역할 제한 | 로그인·허용된 상위 화면; 타인 정보 노출 금지 |
| STATE-09 취소·만료·충돌 | 실제 중단·폐기 여부와 재개 지점 | 새 검토·최신본 비교·재인증 |

**ASYNC-01 필수:** 클릭했다는 이유로 완료로 표시하거나 가짜 진행률·예상 시간을 만들지 않는다.
상태 알림은 초점을 빼앗지 않고 보조기기에 전달한다. 작은 갱신마다 화면 전체를 읽히게 하지 않는다.
[상태 메시지 접근성](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)

**ASYNC-02 필수:** 실시간 갱신에서도 검색·페이지·선택·읽는 위치를 유지한다.
순서가 크게 바뀌면 `새 결과 반영`을 제공하거나 사용자가 선택한 자동 정렬 정책을 따른다.
이벤트 누락·재연결 시 서버 상태와 다시 맞춘다. 연결 여부와 데이터 최신성을 구분한다.
늦게 도착한 응답이 로그아웃·수업 전환 이후 새 문맥을 덮어쓰지 않게 한다.

**ASYNC-03 권장:** 숨겨진 화면이나 연결 단절 시 불필요한 조회를 줄인다. 재시도 간격·횟수 상한과
수동 확인을 제공한다. 브라우저의 조회 중단을 서버 작업 중단으로 설명하지 않는다.

## 8. 교육 업무별 필수 흐름

### 8.1 과제 작성·검증·공개

**EDU-01 필수:** 문제·학생 파일·채점 설정을 하나의 문맥에서 작성한다.
템플릿 받기 → 초안 저장 → 검증 → 수정 → 학생 미리보기 → 공개 흐름을 제공한다.
검증 통과와 공개는 별개다. 새 과제를 만들었다고 자동 공개하지 않는다.
공개·갱신 전에는 대상 분반, 수령 기간, 제출 마감, 학생에게 보이는 내용, 기존 수령·제출에 미치는 영향을 보여준다.
설명 수정과 채점 기준 변경을 구별하고 제출에 적용된 버전을 추적할 수 있게 한다.

### 8.2 학생 수령·작업·공식 제출

**EDU-02 필수:** 다음 단계의 성공을 서로 대신하지 않는다.

| 단계 | 성공 근거 | 실패 시 이어갈 지점 |
| --- | --- | --- |
| 과제 수락 | 해당 학생의 서버 수락 확인 | 인증·권한·수령 기간 확인 |
| 다운로드 | 파일 수신·검증·지정 위치 준비 | 다운로드 재시도; 작성 코드 덮어쓰기 금지 |
| IDE 열기 | 해당 폴더·프로젝트가 열림 | 저장 위치와 `기존 폴더 열기` |
| 서버 저장 | 해당 작업 버전의 서버 저장 확인 | 재시도·내보내기; 공식 제출로 표시하지 않음 |
| 공식 제출 접수 | 서버 접수 ID·시각·코드 버전 확인 | 상태 조회 후 재시도 |
| 채점·결과 공개 | 해당 접수의 채점 상태와 공개 권한 확인 | 상태 재조회·피드백 확인 |

수락 이력, 현재 인증, 로컬 폴더는 서로 다르다. 폴더를 열었다고 로그인·수락됐다고 판단하지 않는다.
과제 전환·다운로드·복원·제출 전에 수업·과제와 작업 폴더가 맞는지 확인한다.
자동 Git add/commit/push도 학생에게는 저장·접수의 실제 결과로 설명하고 충돌·실패를 숨기지 않는다.

### 8.3 점수와 피드백

**EDU-03 필수:** `선택한 제출`, `최신 제출`, `이전 최고점`, `교수자 확정 성적`을 구분한다.
이전 최고점의 범위를 명시한다. 현재 Autograde 결과 화면에서는 **현재 제출을 제외**한 결과다.
실행 중·미제출·비공개·환경 장애를 0점으로 표시하지 않는다. 평가 정책에 따라 확정된 0점은 그대로 표시한다.

**EDU-04 필수:** 공개 정책이 허용한 범위에서 평가 항목, 기대 동작, 관측 결과, 점수·배점,
수정할 위치·다음 행동을 연결한다. `score_only`는 총점만 제공하며 결과 공개 전에는 항목·진단을 노출하지 않는다.
컴파일 실패·실행 오류·오답·미검사·서버 장애를 구별한다. 비공개 테스트 입력·정답을 공개하지 않고도
허용된 평가 요소·힌트를 설명한다. 근거 없는 오류 원인·코드 줄을 지목하거나 통과 수만으로 완성을 단정하지 않는다.
[피드백 공개 계약](../docs/operations/student-grading-feedback.md)

**EDU-05 필수:** 집계에는 학생 수/학생×과제 건수/누적 제출 수와 수업·필터·시점을 표시한다.
이력은 제출 시각 → 코드 버전 → 점수 → 이전 대비 증감 → 코드 비교로 연결한다.
분석은 근거 부족을 표시하며 접속 여부만으로 성실도·학습능력을 판정하지 않는다.
AI 제안·관찰 사실·교수자 확정 평가를 구별하고 분석 결과만으로 성적이나 학생 조치를 자동 변경하지 않는다.

### 8.4 성적표와 학생별 자료

**EDU-06 필수:** 성적표 가져오기는 학번 매칭 → 오류·중복·전체 행 검토 → 공개 항목 선택 →
학생 미리보기 → 기존 공개본과 차이 → 확인 후 공개 순으로 진행한다. 새 열을 자동 공개 선택하지 않는다.

**EDU-07 필수:** 자료 등록은 선택 → 업로드 → 형식·용량·학번 검사 → 매칭 검토 → 적용 순으로 진행한다.
초안은 준비 작업을, 공개 자료는 학생별 배정·요청 확인을 우선 배치한다.
수정·교체·배정 제외에 즉시 반영 여부·대상 수를 표시한다. 자료 변경은 성적 변경과 분리한다.
업로드 전에 지원 형식, 파일당·전체 전송 크기, 압축 해제 크기, 개수·중첩 제한을 안내한다.
한도는 프록시·서버에서 실제 적용되는 설정을 기준으로 제공한다. `413`만 보여주지 말고 초과 기준과
파일 분할 등 해결 방법을 알려준다. 이미 받은 파일을 회수했다고 표시하지 않는다.
파일 요청 기록은 다운로드 완료·열람의 증거와 구별한다.

### 8.5 실시간 교실과 IDE 제어

**EDU-08 필수:** 학생 카드에 연결 상태·마지막 확인 시각, 최근 활동, 공식 제출 여부를 구분한다.
연결 끊김을 결석·부정행위로 단정하지 않는다. 활동 근거·PC 요청은 해당 학생 상세에서 제공한다.
교수자 요청은 보냄 → IDE 전달 확인 → 학생 확인/거절 → 처리 중 → 결과를 실제 지원 계약에 맞게 표시한다.
미지원·오프라인·만료·취소를 구별하고 전달 확인을 작업 성공으로 간주하지 않는다.
강제 종료·덮어쓰기·확장 설치 등 영향 큰 작업은 대상·정책·학생에게 보일 내용을 먼저 검토한다.

## 9. 웹·IDE·공용 실습실의 연속성

**IDE-01 필수:** 일상 작업은 학습 홈·패널에서 수행한다. 명령 팔레트·터미널은 보조 경로로 제공하며
로그인·수령·제출의 유일한 경로로 삼지 않는다.

**IDE-02 필수:** 현재 사용자·수업·과제·서버·저장 상태를 확인할 수 있게 한다.
수령 코드는 붙여넣기를 지원하고 만료·사용 완료·서버 불일치를 구분한다.
웹에서 IDE 열기가 실패해도 설치 안내·코드 입력·기존 폴더 열기로 이어갈 수 있어야 한다.

**IDE-03 필수:** macOS·Windows·Linux, Windows 네이티브·WSL2, 원격 Linux 실행공간을 구분한다.
컴파일러·실행 위치·지원 기능을 검사 결과로 안내한다. OS 감지만으로 도구 설치 완료를 표시하지 않는다.
환경 점검 실패에는 실패 항목·재검사·설치/운영자 안내를 제공한다.

**IDE-04 필수:** 폴더 분리는 OS 보안 격리와 다르다. 원격 실행공간 삭제는 로컬 파일·서버 제출본 삭제와 다르다.
AI 사용 정책도 IDE 내부 제한인지 OS·네트워크 제한인지 범위를 표시하고 미지원 통제를 보장하지 않는다.

**IDE-05 필수 — 공용 PC:** 적용된 서버·실행기 정리 정책을 그대로 설명한다.
`종료 시 삭제`와 `다음 시작 전 정리`를 혼용하지 않는다. 종료·비정상 종료·다음 시작 각각의
파일·로그인 정보·캐시·서버 저장본 처리 범위를 정의한다. 인증 정보는 파일 보존 정책과 분리한다.
정리가 확인되지 않으면 이전 자료를 노출한 채 새 실습을 시작하지 않는다.
마지막 서버 저장 시각과 이후 미확인 변경을 구분하고 저장 실패 시 재시도·내보내기·종료 취소를 제공한다.
전원 차단·강제 종료 전 마지막 변경까지 반드시 복원된다고 약속하지 않는다.

**IDE-06 필수 — 내보내기·복원:** 코드·제출본·강의자료 선택 범위와 저장 위치를 보여준다.
관리되는 임시 작업 폴더 밖으로 내보내며 공용 PC에 남은 사본은 타인에게 노출될 수 있음을 안내한다.
인증 비밀정보는 포함하지 않는다. 기존 코드를 덮어쓰지 않는 복원 경로를 제공하고 복원을 재제출로 처리하지 않는다.

**IDE-07 권장 — 업데이트:** 승인 버전·다운로드·적용 대기·결과·복귀를 구분한다.
수업 중 작업을 중단시키지 않고 적용 시점을 안내한다. 업데이트 실패와 세션 정리 실패를 별도로 진단한다.

## 10. 인증·개인정보·위험 작업

**SAFE-01 필수:** 인증 입력은 붙여넣기·보조 도구를 지원한다. 비밀번호 표시 선택은 상태가 명확해야 하며
공용 PC에서 계정·토큰 자동 저장을 기본 제공하지 않는다. 편의를 위해 인증·CSRF·수업별 접근·버전 검사를 생략하지 않는다.
[접근 가능한 인증](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html)

**SAFE-02 필수:** 연구·수업 개선 동의는 수업 이용과 구분한다. 목적·항목·보관·철회 영향을 설명하고
미응답·동의·거절을 별도 기록한다. 사전 체크·차별적 강조를 피하고 거절을 수업 이용 거절로 해석하지 않는다.
정보 활용 설정에서 선택을 바꿀 수 있게 한다.

**SAFE-03 필수:** 수업 보관·개인별 기록 파기 전 학생 정보와 집계 통계의 처리 범위를 보여준다.
현재 제품의 수업 보관 방향은 동의한 학생의 집계 통계만 보관하고 수업 범위의 개인별 코드·점수·활동 정보를
파기하는 것이다. **개별 과제 보관·휴지통 이동은 제출 이력을 유지하는 별도 작업**이며 이 파기 정책을 적용하지 않는다.
다른 수업에서 필요한 계정·기록을 함께 지우지 않는다. 서버 관리 원본·원격 실행공간·백업·사용자가 내보낸 사본의
처리 범위를 구분하고, 서버가 관리하지 않는 사본까지 삭제됐다고 표시하지 않는다.
비식별화·파기 완료는 처리 확인 후 표시한다. 문구는 실제 보관 정책과 일치해야 하며 정책 변경은 별도 검토한다.
[수업 보관·파기 운영 계약](../docs/operations/institution-operations.md)

**SAFE-04 필수:** 보관·휴지통·영구 삭제·수강 해제·접근 종료를 같은 `삭제`로 표현하지 않는다.
확인 화면에는 대상·범위·복구 여부·기존 제출·공개 자료 영향을 표시한다. 일상 조회·작은 편집마다 확인을 강제하지 않는다.
접근은 차단됐지만 파일 정리가 실패했다면 `접근 차단 완료 · 파일 정리 확인 필요`처럼 실제 결과를 구분한다.

**SAFE-05 필수:** 오류 설명은 원인·영향·다음 행동 중심으로 제공한다. 진단 ID·오류 코드는 상세에 둔다.
토큰·비밀번호·타인 정보·불필요한 내부 경로를 메시지나 로그에 노출하지 않는다.
사용성 분석도 학번·코드·성적 원문을 기본 수집하지 않는다. 필요한 수집은 목적·범위·보관을 정의한다.

## 11. 플러그인·SES 제품 구성과 UX 확장 계약

**MOD-01 필수:** 모듈도 공통 메뉴·토큰·용어·오류·접근성 계약을 따른다.
모듈마다 독립 사이드바·로그인·수업 선택을 복제하지 않는다.
아래는 설계 계약이며 새 실행 스키마나 API가 구현됐다는 뜻은 아니다.

| 항목 | 모듈 설계에 기록할 내용 |
| --- | --- |
| 식별·목적 | 안정적인 모듈 ID, 사용자용 이름, 해결할 작업 |
| 역할·범위 | 허용 역할, 수업·학생·기관 범위, 서버 인가 위치 |
| 탐색 | 메뉴 그룹·순서, 진입·복귀·직접 링크, 활성 조건 |
| 상태 | 설치·선택·검증·활성·기능 저하·중지; 미설정·권한 없음·빈 데이터 구별 |
| 데이터 | 읽고 쓰는 항목, 저장·공개·삭제 정책, 감사 근거 |
| 연계 | 웹·IDE 요구 기능, 지원 계약 버전, 비호환 안내 |
| 설정 | 기관/수업/개인 적용 범위, 적용 시점, 기본값 |
| 인수 | 최소·전체·부분 활성 구성, 권한 차이, 실패 시나리오 |

**MOD-02 필수:** 서버의 권한·기능 계약을 메뉴 원본으로 삼는다. API 이름이나 설치 흔적만으로
사용 가능 여부를 추정하지 않는다. 설계 전용·미구현 모듈을 실행 가능한 기능처럼 표시하지 않는다.
기능 미선택·권한 없음·설정 필요·장애에 따라 적절한 사람에게 다음 행동을 안내한다.

**MOD-03 필수:** 모듈 활성화·비활성화 전 사용자 화면·진행 작업·자료 접근·권한 영향을 검토한다.
기관 사용자 정의 범위는 메뉴 이름·기본 보기·밀도 등으로 정하고, 학생 정보 격리·접근성·명확한 공개 확인은
기관 테마나 모듈 설정으로 제거할 수 없게 한다.

## 12. 성능과 운영 상태의 사용자 경험

**PERF-01 필수:** 느린 응답에서도 버튼 실행 여부와 단계를 보여준다. 실제 완료 시간과 화면 반응 시간을 구분한다.
장시간 채점·업로드·환경 준비는 상태와 복귀 경로를 제공한다. 가짜 완료나 무기한 스피너만 표시하지 않는다.

**PERF-02 권장:** 웹의 초기 목표는 기기군별 75백분위에서 LCP ≤2.5초, INP ≤200ms, CLS ≤0.1로 둔다.
이는 Web Vitals 권장 경계이며 측정 전 달성했다고 표시하지 않는다. 표본이 부족하면 환경·표본 수와
실험실 결과를 구분한다. 성적·코드 원문을 측정 도구에 보내지 않는다.
[측정 기준](https://web.dev/articles/vitals)

**PERF-03 필수:** 기준 PC·네트워크·수강생 수·파일 규모를 정하고 시험한다.
작은 합성 데이터 성공을 대형 수업·느린 실습실의 성공으로 일반화하지 않는다.
페이지 분할·필요한 데이터만 요청·숨겨진 화면 조회 감소로 사용성과 운영 비용을 함께 관리한다.

**OPS-01 필수:** 운영 화면은 확인 시각·영향 수업·문제 항목·확인/복구 행동을 제공한다.
Next.js·외부 접근·채점 작업자·저장소·백업을 각각 확인한다. 프로세스 실행과 실제 기능 이용 가능을 구분한다.
학생에게는 학생이 할 수 있는 행동을, 운영자에게는 진단·복구를 제공한다.

## 13. 문구·용어·시간 표현

**TEXT-01 필수:** 결과 → 이유/영향 → 다음 행동 순으로 짧게 설명한다.
내부 기술 명칭만으로 작업을 표현하거나 잘못을 학생 탓으로 돌리지 않는다.

| 피할 표현 | 권장 예시 |
| --- | --- |
| `처리`, `실행`, `확인`만 있는 버튼 | `초안 저장`, `공개 내용 검토`, `제출 결과 확인` |
| `network_error`만 표시 | `접수 여부를 확인하지 못했습니다. 연결 후 접수 상태를 다시 확인하세요.` |
| `수강 허용 명단 CSV 관리` | 메뉴 `수강생 관리` → 작업 `명단 파일로 등록` |
| `완료` | `서버 저장 확인`, `제출 접수 완료`, `채점 완료` |
| `점수 없음: 0` | `채점 대기 · 점수 미확정`, `아직 공개되지 않음` |
| 서버 요청만 확인하고 `다운로드 완료` | `파일 요청 확인` |

**TEXT-02 필수:** 수령 기간·제출 마감·공개 기간을 별도 표시한다.
판단은 서버 정책·서버 시각을 기준으로 하고 시간대·마감 포함 여부·지각 허용 여부를 설명한다.
`내일`·`5분 남음`만 쓰지 않고 정확한 날짜·시각도 제공한다.
사용자 표기는 `2026. 11. 19. 13:50 (KST)`처럼 통일하고 내부 형식을 그대로 노출하지 않는다.

**TEXT-03 권장:** 문제·평가 안내는 수행할 일, 입력·출력, 제약, 평가 요소, 힌트 순으로 작성한다.
문서만으로 실습할 수 있게 하고 불필요한 수사·아이스브레이킹을 넣지 않는다.
친절함은 구체적 예시와 해결 행동으로 제공한다.

### 14.1 검증 시나리오

다음 중 해당 기능에 적용할 항목을 선택하고 나머지는 사유를 기록한다.

- **흐름:** 직접 링크 → 인증 → 작업 → 결과 → 상위 복귀. 새로고침·뒤로가기·IDE 재시작.
- **문맥:** 검색 후 상세 복귀, 수업·역할 전환, 다른 탭 세션 변경, 제한된 권한.
- **데이터:** 없음·1개·다수·페이지 경계·동명·긴 한글·미제출·0점·새 제출 대기·이전 최고점.
- **실패:** 입력 오류, 업로드 한도, 응답 유실, 부분 성공, 동시 편집, 만료, 권한 회수, 저장소 장애.
- **조작:** 키보드만 사용, 초점 가시성·복귀, Enter/Escape, 터치, 화면 읽기 도구.
- **시각:** 밝은·어두운·고대비, 좁은 IDE 패널, 320/390/803/1324 CSS px, 200% 글자 확대·400% 재배치.
- **플랫폼:** 지원표에 있는 Safari·Chromium·Firefox와 Windows/macOS/Linux·WSL2 해당 조합.
- **공용 PC:** 정상·비정상 종료·다음 시작, 서버 저장 실패, 사용자 교체, 정리 실패, 내보낸 사본.
- **구성:** 필수 모듈만/전체/일부 비활성/구버전 서버·IDE/설정 누락.

작은 수정마다 모든 조합을 반복하지 않는다. 변경 영향에 맞게 회귀 범위를 정하되
지원을 선언할 플랫폼은 출시 전에 검증한다. 자동화는 상태·권한·복구·값의 의미를,
화면 캡처는 배치·가독성을 확인한다. 수동 키보드·화면 읽기 시험도 포함한다.
서버 렌더링 폼은 기존 JavaScript 없는 기본 경로를 유지한다. Next.js·IDE 전체가 JavaScript 없이
동작한다고 보장하지 말고 로딩 실패 시 재시도·지원되는 대체 경로를 제공한다.

### 14.2 실제 사용자 과업 시험

대표 과업은 `과제 등록 후 공개`, `특정 학생 자료 교체`, `미제출 학생 찾기`,
`IDE 수령·제출 후 수정할 항목 찾기`에서 선택한다. 개발자 시연과 사용자 시험을 구분한다.
사용자에게 버튼 위치를 알려주지 않고 목적만 제시한다. 초보·반복 사용자, 교수자·학생,
필요한 보조기기 이용자를 포함한다. 초기 역할별 소수 참여자 시험을 통계적으로 대표하는 결과로 주장하지 않는다.

| 측정 | 기록 방법 |
| --- | --- |
| 완료율 | 도움 없이/도움 후/실패, 성공 정의와 참여자 수 |
| 오류 | 잘못된 수업·대상·공개, 반복 입력·중복 제출, 복구 여부 |
| 시간 | 시작·종료 지점, 조작 시간과 서버 대기 구분 |
| 탐색 | 잘못 간 화면·되돌아감·검색 재입력과 원인 |
| 이해 | 저장·접수·채점·점수 의미를 사용자 말로 설명하게 함 |
| 주관 평가 | 어려웠던 부분·이유; 관찰 사실과 사용자 의견 분리 |

개선 전후는 같은 난이도의 과업·데이터·환경으로 비교한다. 목표 시간·완료율은 시험 전에 정하고
결과에 맞춰 사후 변경하지 않는다. 관찰 없이 `UX 90점` 같은 종합 점수를 만들지 않는다.

### 14.3 출시 판정과 예외

| 수준 | 예시 | 처리 |
| --- | --- | --- |
| P0 | 타인 정보 노출, 의도치 않은 공개, 복구 불가능한 손실 | 출시 중단·즉시 수정 |
| P1 | 핵심 과업 불가, 접수 성공 오표시, 지원 기기의 키보드 사용 불가 | 출시 전 수정 또는 사용 가능한 범위로 출시 축소 |
| P2 | 우회 가능한 혼란·중복 입력·느린 조회 | 담당·기한·대안을 정해 계획 |
| P3 | 작업 영향이 작은 정렬·간격·문구 | 공통 컴포넌트 개선에 묶어 관리 |

필수 기준의 예외에는 규칙 ID, 이유, 영향 사용자, 대안, 검증 근거, 책임자, 해소 기한을 남긴다.
P0/P1을 디자인 예외로 승인하지 않는다. 기한 없는 예외나 미검증 플랫폼의 정상 동작 주장을 허용하지 않는다.
출시 기준은 `대상 범위의 P0/P1 없음 + 필수 검사 증거 + 잔여 결함 공개 + 배포·복귀 확인`이다.

소규모 팀에서 한 사람이 여러 역할을 맡아도 확인 항목을 생략하지 않는다.
